## 🟠 Important

### A shutdown-killed verify is reported as a genuine measured failure, not an abort
**`extensions/goal.ts:1058`** — found by robustness, tests
`session_shutdown` kills live verifies with `killVerifyTree` (goal.ts:1058) but does not mark them. The pending `runVerify` therefore takes the ordinary `close` path (goal.ts:325-327) and resolves `{ok: false, exitCode: null, timedOut: false, output}` — `aborted` is only ever set by the signal listener (goal.ts:317-318) and `timedOut` only by the timer (goal.ts:310-312). Both new consumers branch on `aborted`: the completion gate (goal.ts:1448-1456) and the settle loop (goal.ts:1214-1220). So when a session replacement/reload (agent-session.js `reload()` emits `session_shutdown` with reason "reload", dist/core/agent-session.js:2870, without waiting for idle) tears down an in-flight completion check, the model is told `NOT completed — verify exited ?. Output: ... Fix the failure, then call complete again with fresh evidence` — a fabricated measurement — and in the settle loop the killed result is cached as the measured state and counts as a continuation (`lastCheck = check`, `continuations += 1`, goal.ts:1221-1229) instead of being dropped like a real abort.

**Fix**: Give the shutdown kill its own outcome (e.g. have `killVerifyTree`-by-shutdown set a `killed: true` / `aborted: true` flag on the result, or have the handler call the same `finish` path with `aborted: true`) so callers treat a teardown kill the same as an Esc abort: no continuation burned, no false "verify failed" reported to the model.

## 🟡 Suggestion

### The new group kill no-ops exactly when descendants outlive the shell — the case it was added for
**`extensions/goal.ts:243`** — found by robustness
`killVerifyTree` bails out whenever `exitCode`/`signalCode` is set (goal.ts:243), i.e. once the shell itself has exited and been reaped. But the group `-pid` can still contain live members at that point, and that is the documented failure mode of this spawn style: pi's `waitForChildProcess` exists precisely because "a short-lived child can `exit` while a detached descendant keeps its stdout/stderr pipe open" (dist/utils/child-process.js:12-21, earendil-works/pi#5303, referenced by lib/superbash.ts:40). For `runVerify` that means: a verify that backgrounds work (`gate.sh &`, a spawned server/migration) makes `sh` exit immediately while the descendant holds the piped stdout/stderr, so `child.on("close")` (goal.ts:325) never fires, the timer at goal.ts:310 eventually fires and calls `killTree()` → guard returns early → the descendant is never killed and keeps running (locks/GPUs held), while the caller is told `timedOut: true` — a false failure. The abort (goal.ts:317) and `session_shutdown` (goal.ts:1058) kill paths are skipped by the same guard.

**Fix**: Track the group separately from the leader: only skip the group kill when the whole group is gone (e.g. probe with `process.kill(-pid, 0)` and kill when it still resolves, or record whether the child was ever a group leader and accept the narrower pid-reuse risk the comment already documents for the abort path); otherwise the orphaned-descendant case the change targets is still unreachable.

### Verify is now spawned detached with a private kill-set, so a model-authored check can outlive every cleanup path except a clean session_shutdown
**`extensions/goal.ts:296`** — found by security, robustness, tests
This diff makes runVerify spawn the goal's `verify` command — an arbitrary shell command authored by the model, run with the user's full privileges — with `detached: true` (extensions/goal.ts:296), i.e. the child becomes the leader of its own session/process group and is no longer in pi's process group. Its only reapers are (a) the run's own timeout timer, which is `unref`'d (goal.ts:312-314) so it dies with the host process, and (b) the module-level `liveVerifyChildren` set drained in `session_shutdown` (goal.ts:230-233, 1054-1060). `session_shutdown` does not run on an uncaught-exception crash or an emergency terminal exit, and pi's detached-child reaper is never told about these pids: pi's own bash tool spawns detached AND registers the pid with the platform tracker (`trackDetachedChildPid`, node_modules/@earendil-works/pi-coding-agent/dist/core/tools/bash.js:65-77, untracked at :117-119), and that tracker is what pi flushes on the crash paths it does handle (dist/modes/interactive/interactive-mode.js:3422 and :3448, dist/modes/rpc/rpc-mode.js:282, dist/modes/print-mode.js:38). The goal extension bypasses it, even though the same repo's lib/superbash.ts deliberately routes background shell work through the platform's local bash operations for exactly this reason (lib/superbash.ts:36-41: 'identical process-tree kill, identical #5303-safe wait on detached descendants'). Detaching also removes the previous backstop: a non-detached child sat in pi's foreground process group, so closing the terminal delivered it SIGHUP, whereas a child in its own session with no controlling terminal never receives it. Consequence: after pi dies mid-check (crash/emergency exit, or a terminal close after either), the detached verify keeps running with no bound — holding locks and GPUs and continuing to write to the repo after the user believes the session ended; this is the exact failure the new comments describe observing ('gate logs still growing six minutes after pi was killed'), and…

**Fix**: Run the verify through the platform's bounded shell boundary instead of a hand-rolled spawn — `createLocalBashOperations()` (`ops.exec(command, cwd, { signal, timeout, env })`, the public export the rest of this repo uses in lib/superbash.ts) registers the detached child with pi's tracker and performs the same process-group kill, so the crash/signal/emergency-exit paths reap it; if a raw spawn is kept, do not detach (so the terminal's SIGHUP still reaches an orphaned check) and/or supply the child its own bounded lifetime rather than relying on an unref'd in-host timer.

### Settle-path forwarding of ctx.signal to the verify runner is untested
**`extensions/goal.ts:1199`** — found by tests
The settle handler now passes `signal: ctx.signal` into `verifyRunner` (goal.ts:1199) so `session.abort()` isn't wedged behind a multi-minute verify. The new settle test (tests/goal.test.ts:986) sets `signal: undefined` on its ctx and simulates the abort by having the injected runner *return* `{ aborted: true }`, so it exercises the `check.aborted` branch but never the wiring. The only signal-forwarding assertion (tests/goal.test.ts:697) covers the tool-execute path, not this call site. Deleting `signal: ctx.signal` here — reintroducing the wedge the comment warns about — would not fail any test.

**Fix**: Add a settle test that supplies a real AbortController's signal on ctx, aborts mid-check, and asserts the runner received that signal (and that the handler resolves without queueing a follow-up).

### throwToVerifyResult (the tool-path runner-rejection conversion) is never exercised
**`extensions/goal.ts:1298`** — found by tests
`runGatedVerify` wraps the runner in try/catch and converts a thrown error via the new `throwToVerifyResult` helper (goal.ts:1298, 1336-1339). Before this diff the set/complete paths called `verifyRunner` directly with no try/catch, so a throwing injected runner propagated; now it is turned into a `spawnError` result. No test drives a throwing runner through the set or complete tool path — the only throwing-runner tests seed the goal via `session_start` to hit the *settle* branch (tests/goal.test.ts:1388, :1550), which uses its own inline catch, not `throwToVerifyResult`. The helper has zero coverage, so the new swallow-and-report behavior is unprotected.

**Fix**: Add a test registering `registerGoalTool(pi, { verifyRunner: async () => { throw new Error("boom"); } })` and asserting a `set`/`complete` tool call resolves (does not reject) with the failure text rather than throwing out of `execute`.
