### Report path is built from an unsanitized tool-call id, allowing path traversal on write
**`extensions/review.ts:1538`** — found by security, robustness
The diff replaces the fixed `.pi/review-report.md` filename with `path.join(reportDir, `${id}.md`)`, where `id` is `execute(id, params, signal, _onUpdate, ctx)`'s first argument (line 1507) — the tool-call id assigned by the harness/provider, which the extension does not control (pi's own nested/codemode calls even produce ids of the form `<parentId>/<n>`, containing `/`). The id is interpolated with no sanitization, and `writeFile` there uses `mkdir(path.dirname(p), { recursive: true })` then `writeFile(p, data, ...)`, so a crafted id containing `..` segments (e.g. from a hostile/quirky provider returning an attacker-chosen tool_call id) resolves outside `.pi/review/` and writes the report content to an arbitrary `<chosen>.md` path under the repo/process cwd. The previous fixed filename had no such input-to-path surface, so this diff introduces it.

**Fix**: Sanitize the id before use (strip/reject path separators and `..`, e.g. keep only `[A-Za-z0-9._-]`), or ignore the id entirely and derive the filename from a generated UUID/counter, and verify the resolved path stays within reportDir.

### New abort handling is only tested on the pre-flight path; the fail-open guard it protects is unverified
**`tests/review.test.ts:750`** — found by tests
This change adds three abort checks to runReview (extensions/review.ts:1251 pre-flight, :1292 after the finders settle, :1340 inside the verify `catch`) and threads `signal` into the finder/verifier runChild calls (:1279, :1331). The added test aborts the controller before runReview runs any stage, so only the pre-flight check at :1251 fires (it throws before anything spawns, which is why `spawn.tasks` is empty). The check at :1340 is the one the new docstring justifies — "abort never rides the fail-open path, which would complete a cancelled review instead of stopping it" — because the surrounding catch runs `bundle = { findings: candidates, rejected: [], unverified: true }` and returns a completed review. That path (abort during verification) and the abort-during-finders path (:1292) are never exercised: a regression that deleted :1292/:1340, or that let an aborted verify fall through to the fail-open bundle, would still leave this test green while a cancelled `/review` or `review` tool call silently reports success.

**Fix**: Add a case where the fake spawn aborts the shared AbortController mid-flight (e.g. the finder `child` fires abort before its `close`) and assert runReview rejects with "review aborted" and never reaches renderReport; and a case where abort fires during the verify child, asserting the fail-open `unverified: true` bundle is not returned. Keep the existing pre-flight case (it correctly asserts zero spawned children).

### Abort mid-run still spawns the remaining queued finder children before killing them
**`extensions/review.ts:1273`** — found by robustness
runWithLimit (extensions/subagents.ts:643-661) never checks the signal: when an abort rejects the in-flight jobs, each freed worker pulls the next queued job, and runChild spawns the process *before* it inspects the signal (`const child = spawnFn(...)` at subagents.ts:457, `if (signal?.aborted) onAbort()` at ~520 — asserted by the existing test at tests/subagents.test.ts:750). So after an Esc during the finder stage, up to `maxChildren - 4` further `pi` processes are forked and immediately SIGKILLed, and runReview keeps draining the queue before its post-batch `if (signal?.aborted) throw` (line 1292) fires. The new test's claim that "cancellation must not burn tokens" only holds for the pre-aborted case it covers (spawn.tasks === 0).

**Fix**: Short-circuit inside the job factory instead of relying on runChild's registration check: `if (signal?.aborted) throw new Error("review aborted");` as the first statement of the mapped closure at line 1268, and/or add the same check to runWithLimit's job pull so a cancelled batch stops dispatching.
