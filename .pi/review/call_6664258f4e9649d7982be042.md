## 🟠 Important

### The deferral's premise (a completion wake re-engages the agent) fails for never-ending or killed tasks, parking the goal loop
**`extensions/goal.ts:1277`** — found by correctness, robustness
The new guard (`const running = runningTasks(); if (running.length > 0) { … setStatus/notify …; return undefined; }`, goal.ts:1277–1298) returns before the continuation-cap/judge block and never increments `continuations`, so the park has no bound: no deferral counter, no wall-clock deadline. `TaskRegistry.running()` counts only `state === "running"` (lib/superbash.ts:355–360), `killTask` flips state to "killed" without delivering a wake, and `complete()` is fire-once ("killed tasks never wake", lib/superbash.ts:321–330). So a task that never exits (the tool's own docs advertise dev servers/watchers for background bash and `task_remind`) or one killed while the loop is parked produces no wake, and the goal loop stays parked with only the footer `goal · holding check — N background tasks running`/task …` until a later user prompt. The notice text is now accurate about the recovery (goal.ts:1293–1296: "kill it (/tasks or task_kill): the check then runs on your next prompt"), but the loop stops driving the goal for the task's whole lifetime, and nothing bounds it. This same change makes the park reachable in production: the previous round's holder was module-scoped, so `getSharedTaskRegistry()` never connected goal's reader to subagents' writer under pi's per-extension jiti loader; the new `Symbol.for` global holder (lib/superbash.ts:394–432) makes the deferral actually fire, so this path is no longer dead code. The added tests cover only defer→calm (tests/goal.test.ts:1123–1200), so the never-finishing/killed shapes are unguarded.

**Fix**: Bound the park instead of making it unconditional: record the first deferral (counter or timestamp) and, after N deferrals or a grace deadline, run the check anyway with a notice naming the still-running tasks; or scope the guard to tasks that can actually conflict with the verify.

### A bare Esc aimed at another component (dialog/autocomplete dismiss) SIGKILLs the verify's process tree and re-engages the loop, because raw terminal input is accepted as the kill command
**`extensions/goal.ts:1369`** — found by correctness, security, robustness
The kill command is still unattributed raw bytes. `listenForTerminalInput` (goal.ts:478-486) subscribes to `ui.onTerminalInput`, and pi-tui dispatches raw input to those listeners *before* the focused component (`for (const listener of this.inputListeners) { const result = listener(current); … }`, node_modules/@earendil-works/pi-tui/dist/tui.js:685-699), so an Esc the editor consumed is still seen here — the editor consumes Esc for an open completion popup and returns without calling onEscape (pi-tui/dist/components/editor.js:601-606). Two such dismissals inside the new 3 s window are two consecutive bare Escs, so they pass the confirm (`matchesKey(data, "escape")`, ESC_CONFIRM_MS = 3_000, goal.ts:225/1369-1377) and `escAbort.abort()` reaches runVerify's kill switch — `process.kill(-child.pid, "SIGKILL")` on the check's whole process group (goal.ts:337-345) — i.e. an unrelated popup dismissal SIGKILLs a state-mutating verify (migration, artifact rewrite, gate script holding a lock) mid-write. It then also queues a visible "aborted before it finished" follow-up and returns `{continue: true}` (goal.ts:1418-1438), buying an extra autonomous model turn. Two further collisions came with the same gesture: the extension's own hint tells the user "esc twice to abort" (goal.ts:1356), and with an empty editor two Escs <500 ms apart also fire pi's double-escape action (interactive-mode.js:2343-2360: `/tree` or `/fork`), so following the hint can open the session-tree selector whose navigation aborts the session; and the first Esc is not free either — at this boundary `session.isStreaming` is true (it is `_isAgentRunActive`, set for the whole run, agent-session.js:1025/1320), so the editor's onEscape runs `restoreQueuedMessagesToEditor({ abort: true })` → `session.abort()` (interactive-mode.js:2331-2334), which sets `_abortDuringBeforeSettle` (agent-session.js:1848-1849) so the boundary returns false and the goal's own continuation is dropped regardless — the docstring's "a sin…

**Fix**: Attribute the key instead of counting presses: don't treat raw Esc as the kill command (use a check-owned chord or an explicit `/goal` action), or at minimum only arm/confirm on input the editor did not consume, and do not overlap pi's own double-Escape window.

### The shared-registry tests cannot detect a regression to the module-scoped holder — the exact failure this change exists to prevent
**`tests/goal.test.ts:1206`** — found by tests
This change replaces a module-scoped holder with a `Symbol.for` process-global specifically because, per the new comment in lib/superbash.ts ("...a module-scoped holder would silently never connect writer to reader (the deferral would no-op in production while working in tests, which share one module graph)"), goal and subagents hold separate copies of lib/superbash under pi's jiti loader. The new tests that claim to cover this never exercise two instances: tests/goal.test.ts:1206 imports `publishSharedTaskRegistry`/`getSharedTaskRegistry` from `../lib/superbash` and publishes+reads through that one instance, and tests/subagents.test.ts:1174 does the same — neither forces a second module instance. Both would pass unchanged if someone reverted the holder to a module-scoped object (or to a per-file WeakMap), i.e. the production no-op would go undetected. The tests give false confidence about the one mechanism the diff is about.

**Fix**: Add a test that loads lib/superbash twice (e.g. `vi.resetModules()` + a fresh dynamic `import('../lib/superbash')`, or two entry modules) and asserts a registry published via instance A is visible through `getSharedTaskRegistry()` from instance B; that is the only shape that fails for a module-scoped holder.

### The exit→close gap is a wall-clock proxy, so an event-loop stall between the two callbacks fails a passing verify
**`extensions/goal.ts:399`** — found by correctness, robustness
Unchanged by this diff and still valid: `runVerify` decides a verify backgrounded its work partly by comparing wall-clock timestamps stamped in two different libuv callbacks — `exitedAt` in `child.on("exit")` and the verdict `const heldByDescendant = exitedAt !== undefined && Date.now() - exitedAt > EXIT_TO_CLOSE_GRACE_MS` (goal.ts:399, grace 250 ms at goal.ts:283) in `child.on("close")`. Any synchronous parent work between the two callbacks (another extension's CPU-bound handler, a large parse, a GC pause) longer than the grace makes `heldByDescendant` true for a foreground verify that exited 0, and the check is then graded as `spawnError: "verify left background processes running; a verify must run its check in the foreground and exit"` (goal.ts:401-414): a green check is reported as a failure at the settle boundary, the loop re-engages on that false failure, and `action: "complete"` refuses a goal that is in fact met. The companion probe on the same line, `groupAlive(child.pid)`, is sound — it queries the process group directly; only the clock comparison is a proxy.

**Fix**: Keep `groupAlive(child.pid)` as the verdict and turn the timestamp gap into a bounded re-probe: after `close` with code 0, re-check `groupAlive` once after the grace window and fail only if a group member is still alive.

### parkedForTasks is cleared only by a calm settle, so a later park can still be silent although the code promises one notice per park
**`extensions/goal.ts:1288`** — found by correctness, robustness
The revision added `parkedForTasks = false` at goal.ts:1141 (`resetContinuationBudget`) and goal.ts:1155 (`adoptBranchState`), which covers `/goal resume`, a `/goal <objective>` kickoff (that path calls resetContinuationBudget, goal.ts:1862) and session_start/session_tree — but not the model's set path: `setGoal` (goal.ts:1165-1183) clears budgetOutputs/lastCheck/lastCheckAge and leaves the flag true. Sequence that still leaks: goal #1 parks on a long task (notice fires, flag true) → the model sets a new goal with the task still running → every subsequent settle defers for the new goal with `parkedForTasks` already true, so the notice at goal.ts:1290-1294 never fires again, although its comment promises "the notify fires once per park" (goal.ts:1099-1101) and the footer is the only remaining signal for a park that may last the task's whole lifetime.

**Fix**: Clear parkedForTasks wherever a new goal engagement starts (setGoal, and the complete/stop/pause command paths) so each park re-announces once.

### The Esc-confirm test never exercises the ESC_CONFIRM_MS window, and its "arrow key must not arm" assertion is vacuous
**`tests/goal.test.ts:1325`** — found by tests
In `Esc aborts the settle check through the terminal-input listener`, `press("\x1b[A")` (line 1325) is immediately followed by `press("a")` (line 1326) before the arrow key's effect is observed. Because "a" resets `escArmedAt`, the following `expect(settleSignal?.aborted).toBe(false)` (line 1327) is true whether or not the arrow sequence armed the timer, so the comment's claim ("must not arm") is not actually asserted — a regression where `matchesKey("\x1b[A","escape")` returned true (arming on navigation keys) would pass. Separately, the code's time-based branch (`Date.now() - escArmedAt <= ESC_CONFIRM_MS` at extensions/goal.ts:1374 — the window expiry that re-arms rather than confirms) is never covered; the only reset path tested is "another key" (the "x" press).

**Fix**: Assert the arrow key in isolation — `press("\x1b[A")` then `press("\x1b")` and expect no abort (arming would have confirmed) — and add a fake-timer/`Date.now` case that presses two bare Escs more than ESC_CONFIRM_MS apart and expects no abort.
