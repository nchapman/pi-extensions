**`extensions/goal.ts:1237`** — found by robustness
The settle handler passes `signal: ctx.signal` into verifyRunner with the comment "The settle boundary is Esc-abortable too: session.abort() waits for this handler, so an unkillable 15-minute verify here is the same wedge as the tool-call one" (goal.ts:1234-1237). **Fix**: Do not rely on ctx.signal at agent_before_settle: bound the settle check itself (run it through the tool-call path where pi supplies a live signal, or race verifyRunner against a shorter settle-specific cap such as AbortSignal.timeout), and fall back to `ctx.signal ?? AbortSignal.timeout(<cap>)` rather than passing undefined. Correct the comment (and README) to state that only the set-time/completion checks are Esc-abortable, and add a test that drives the settle handler with `signal: undefined` (as pi does) and asserts the check is still bounded and reported as aborted.

### No test observes the process-tree kill — the change's headline claim survives a no-op killGroup
**`extensions/goal.ts:300`** — found by tests
The diff's central promise (README.md:33 "Esc aborts them (killing the verify's whole process tree)"; docstrings at goal.ts:257-260 and 1345-1350) rests entirely on `killGroup` (goal.ts:300-311), the only code that kills the detached group (`process.kill(-child.pid, "SIGKILL")`); it is called by the abort handler (goal.ts:320), the timeout (goal.ts:343) and the leftover branch (goal.ts:354). The three tests that reach those calls assert only result fields and elapsed time: `it("kills a running verify and resolves as aborted when the signal fires")` (tests/goal.test.ts:585-595 asserts `aborted`/`ok`/`timedOut`/`< 5000ms`), `it("times out a long command and kills it")` (:569-574) and `it("never passes a verify that backgrounds its work — leftovers are killed and reported")` (:596-607, which asserts the `spawnError` text the close handler sets, not that anything died). Every one of those outcomes is produced regardless of the kill: `onAbort` calls `killGroup()` and then `finish({aborted:true})` unconditionally (goal.ts:318-322), and the leftover branch sets its message before calling `killGroup`. So replacing `killGroup`'s body with a no-op leaves the whole suite green while each of those tests orphans a live `sleep 30` — i.e. the exact regression the change was written to prevent (an orphaned gate suite holding locks/GPUs after Esc) is not detectable.

**Fix**: Make the kill observable: have the verify record a pid (`sh -c 'echo $$ > <pidfile>; exec sleep 30'`, and for the descendant case `sleep 30 & echo $! > <pidfile>`), then after the abort/timeout/leftover report poll `process.kill(pid, 0)` and assert it throws ESRCH (range under the test's timeout), so a shell-only or absent kill fails the test.

### The leftover-process probe and group kill only run on the exit-0 path, so a failing verify still orphans its background descendants past the session
**`extensions/goal.ts:353`** — found by correctness, security, robustness
Still valid, but only for the residual shape. What is now closed: `runVerify` (extensions/goal.ts:269-368) spawns with `shell: true, detached: true`, so the shell is its own process-group leader (pgid == child.pid), and on `close` it additionally probes `groupAlive(child.pid)` (goal.ts:240-247, called at 353) = `process.kill(-pgid, 0)`. That makes the plain in-group case fail closed — `verify: "sleep 30 >/dev/null 2>&1 &"` exits 0 with a live member still in the shell's group, so line 355-363 reports it instead of a pass (covered by the new test at tests/goal.test.ts:600). What is still open: the probe only sees members of the shell's own process group, and its `ESRCH` result is indistinguishable from "the check really finished". Any check that hands its work to a process that leaves the group — `setsid ./gate.sh >/dev/null 2>&1 &`, a double-forking/daemonizing script, `systemd-run --user ./gate.sh`, `at now < gate.sh` — leaves the shell's group empty (the delegated process has a different sid/pgid by construction; `setsid()` guarantees it), so `groupAlive` returns false, line 365 returns `{ ok: true, exitCode: 0 }`, and the completion gate at goal.ts:1491 marks the goal complete while the gate suite is still running. Precondition for the bypass: the delegated process must also release the inherited stdio pipes (real daemonization and service managers do; a bare `cmd &` does not and is caught). This is exactly the scenario the change's own comment (goal.ts:349-352, "live leftover members mean the check has not finished, which is reported ... rather than counted as a pass") and the README line ("Esc kills the verify's whole process tree — a heavyweight gate suite must never look wedged") present as closed, and it defeats the stated purpose of running the verify outside pi's bash backend. Impact is bounded by the fact that the verify command is supplied by the user/model (and `validateVerify` only blocks `true`/`:`/`exit 0`), so this is a defense-in-depth gap rather t…

**Fix**: Probe and clean the group on every `close`, not just exit 0 — e.g. before the generic `finish({ ok: code === 0, ... })`: `if (child?.pid !== undefined && groupAlive(child.pid)) { killGroup(); finish({ ok: false, exitCode: code, timedOut: false, spawnError: "verify left background processes running; a verify must run its check in the foreground and exit", output: cap() }); return; }` (keeping the exit code so the model still sees the real failure), or at minimum keep the abort registration alive while the group is still non-empty.

### The aborted-settle test cannot detect the stale cache it exists to rule out (checkEvery defaults to 1)
**`tests/goal.test.ts:1090`** — found by tests
The comment at tests/goal.test.ts:1086-1087 promises "The next settle re-measures (nothing cached from the aborted run)", but the tool is registered without `checkEvery` (tests/goal.test.ts:1080-1081), and GOAL_CHECK_EVERY_DEFAULT is 1 (goal.ts:174), so `due = (continuations + 1) % checkEvery === 0` (goal.ts:1223) is true on every settle: the second settle calls the runner no matter what `lastCheck` holds, and `toContain("1/10")` passes either way. A regression that cached the aborted result before the `check.aborted` early return (goal.ts:1254-1260 — the invariant the comment names) therefore does not fail this test. The same regression is user-visible with `checkEvery > 1`, because `check.aborted` is inspected only inside the `due` branch: the reuse branch (goal.ts:1266-1269) would serve the aborted result as an ordinary failure and renderCheckPrompt reports it as "it exited ?" (goal.ts:765), handing the model a fabricated failure the settle path is supposed to avoid.

**Fix**: Register the tool with `checkEvery: 2` (or 3) here and assert the second prompt carries the fresh measurement (`toContain("expected 2 to be 3")`, which the cached-aborted reuse path — empty output, "measured 1 continuation(s) ago" — cannot produce), or count runner invocations.
