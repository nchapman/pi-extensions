## 🟠 Important

### Verify-path settles also run the milestone judge — a second model call is spawned per check, its verdict is discarded, and the child is never drained
**`extensions/goal.ts:1868`** — found by correctness
The `assessed` IIFE is constructed unconditionally inside `if (due)` (goal.ts:1868-1880) and calls `settleJudge!.assess(...)`, but only the judged branch consumes it (`if (judged) { await Promise.race([assessed, killed]) }`, goal.ts:1881-1885; `verdict`/`judgeError` are read only under `if (judged)`, goal.ts:1960-1974). `settleJudge` is registration-scoped and non-undefined by default (`parseJudgeEnabled(undefined) === true`, goal.ts:1484-1493), and `judged = !goal.verify` is false only for goals WITH a verify — i.e. exactly the primary verify-driven flow. So on every due settle for a verify goal the extension builds a full work digest (goal.ts:1871) and calls `createLlmSettleJudge.assess` → `runChild` → `spawn("pi", ... --tools "")` (subagents.ts:453-455, buildChildArgs): a real, metered session-model (or PI_GOAL_JUDGE_MODEL) child per continuation, up to PI_GOAL_JUDGE_TIMEOUT_MS (default 180s). Because nothing awaits `assessed` on that path, the child keeps running after the verify row is rendered and the settle returns, and because the drain closure is registered only for the judged path (`if (judged) liveCheckAborts.add(drain)`, goal.ts:1849), `/goal pause` (goal.ts:2374), `/goal stop` (goal.ts:2422) and `session_shutdown` (goal.ts:1659) do NOT kill it — only alt+x (killAbort, before the key listener is detached) or the 180s timeout does. A failing/timing-out stray child is silently swallowed into the unused `judgeError`. Tests cannot catch this: every verify-path settle ctx omits `sessionManager` (e.g. tests/goal.test.ts:1760, 2482, 2650), so `buildWorkDigest(ctx.sessionManager.getBranch())` throws a TypeError before `assess` is reached, while real pi always supplies `ctx.sessionManager` (ExtensionContext.sessionManager is non-optional) — the same field the judged path relies on (goal.ts:1871, 1578).

**Fix**: Build and await the assessment only when judged — move the `const assessed = (async () => {...})()` block inside `if (judged)` (or guard it with `judged`), so a verify-driven goal never calls the settle judge; optionally add a regression test that registers a spy `settleJudge` on a verify goal with a sessionManager-bearing settle ctx and asserts `assess` is not called.

### Judge prose becomes the continuation window's measured state — a plateau reads as progress and resets the cap
**`extensions/goal.ts:1967`** — found by robustness
On the judged path `check.output` is set to the judge's free-text reason (goal.ts:1961-1967), and that same value is what the budget window records: `if (due) recordBudgetOutput(budgetOutputs, check.output)` (goal.ts:1981). At the cap the default breaker is `defaultProgressJudge`, which only compares the first and last window entries with exact string equality (`outputs[0] !== outputs[outputs.length - 1]`, goal.ts:553-563) and returns `continueRun: true` whenever they differ; the handler then zeroes the counter and grants another full budget, up to PI_GOAL_MAX_PROGRESS_RESETS (default 3) times (goal.ts:1783-1793). A verify's stdout is stable when nothing changes, so that equality test can detect a plateau; a judge's reason is generated prose whose input (the work digest) changes every turn even when the goal does not, and SETTLE_JUDGE_AGENT explicitly instructs the judge to keep answering "working" on a plateau and "say so in the reason" (goal.ts:763) precisely so the caller's progress judge can catch it — a mechanism string equality cannot implement. So for the verify-less goals this change turns on by default, the reset path is effectively always granted and PI_GOAL_MAX_CONTINUATIONS (25) is silently a ~100-continuation budget (each continuation is a full model turn with tools), i.e. the breaker the README/diff lean on ("the cap stays the breaker") is multiplied exactly on the new path. The new cap test only pins the maxContinuations=1 case, where the window holds a single sample and the stop comes from "not enough measured states" rather than from plateau detection, so it does not exercise this.

**Fix**: Record a stable measured state for judged goals instead of the prose — e.g. `recordBudgetOutput(budgetOutputs, `${lastCheckKind}:${[...(verdict?.remaining ?? [])].sort().join("|")}`)` — or have the judge return an explicit `moved: boolean` that defaultProgressJudge honors; keep the reason for the prompt and transcript only. Add a test with the default maxContinuations and a judge whose reason wording varies each call, asserting the loop stops at the cap rather than resetting.

### Judge kill/drain path is untested — the abort test can't catch that no signal reaches the judge child
**`tests/goal.test.ts:565`** — found by tests
The new tests cover the seam, not the child. `the kill key (alt+x) aborts an in-flight judge — the signal reaches the seam` (tests/goal.test.ts:1988) injects a fake `settleJudge` and only asserts the signal handed to `assess` is aborted (`expect(judgeSignal!.aborted).toBe(true)`, line 2030); `an administrative drain unblocks the boundary even against a signal-ignoring judge` (line 2036) injects a judge that never resolves. Neither touches `createLlmSettleJudge`'s child call, and its unit tests record only the runner's `timeoutMs` (`seen.push({ agent, task, model, timeoutMs: options.timeoutMs })`, line 565) and never pass a `ctx.signal` into `assess`. So the line that makes the previous review's bug fixed — `{ timeoutMs, ...(ctx.signal ? { signal: ctx.signal } : {}) }` at extensions/goal.ts:822 — is entirely unasserted: deleting it keeps every test green while alt+x / `/goal pause` / `/goal stop` / `session_shutdown` again fail to kill the judge child (runChild only kills via `options.signal`, extensions/subagents.ts:544-552). The settle boundary would still unblock (the `killed` race at goal.ts:1849-1858), so the failure is invisible in the suite and only shows up as an orphaned `pi` child burning model tokens past the boundary — exactly the symptom the fix and the README claim ('killable with alt+x ... killed by /goal pause//goal stop/reload') exist to remove.

**Fix**: In the createLlmSettleJudge tests, record `options.signal` alongside `timeoutMs` and add a case that passes `{ signal }` into `assess` and asserts the same signal object (already aborted) reaches the runner — the judge-side analog of the verify test that asserts the runner receives the signal.

## 🟡 Suggestion

### parseSettleVerdict discards a valid verdict whenever the judge's reply contains any nested JSON object
**`extensions/goal.ts:662`** — found by correctness
`text.matchAll(/\{[^{}]*\}/g)` cannot span a nested `{`: for a reply such as `{"verdict":"working","reason":"...","remaining":["a"],"evidence":{"criterion":1}}` the engine cannot match the verdict object (the inner `{` blocks `[^{}]*`) and falls through to matching `{"criterion":1}`, which has no `verdict` key — so the function returns undefined and the settle handler records `judge: "unavailable"` with output "the judge returned no opinion" (goal.ts:1961-1974) and sends the generic "could not assess this turn" continuation (goal.ts:1197-1202 via 1986-1995), losing both the complete/blocked steer and the `remaining` list while still burning a continuation (asserted by tests/goal.test.ts:1920-1936). The docstring at goal.ts:656-658 promises "the first brace group that parses as JSON with a valid verdict wins; anything else is no opinion", and the judge prompt invites extra structure (it asks for evidence-based skepticism), so a stray nested field silently disables the feature for that turn.

**Fix**: Scan for balanced braces instead of a single-level regex (e.g. find each `{`, then extend to the matching `}` by depth counting and JSON.parse each candidate), so a nested extra field cannot hide a valid verdict.

### Verdict value is compared unnormalized while reason and remaining are trimmed
**`extensions/goal.ts:667`** — found by correctness
`SETTLE_VERDICTS.includes(obj.verdict as ...)` (goal.ts:666-668) compares the raw string against the lowercase literals, whereas the same branch trims the free text (`obj.reason.trim()`, `r.trim()` at goal.ts:670-674). A reply of `{"verdict":" Working "}`, `{"verdict":"Working"}` or `{"verdict":"COMPLETE"}` therefore parses as no opinion: `lastCheckKind` becomes "unavailable", the agent gets the generic continuation instead of the complete/blocked steer, and the turn's budget is spent (goal.ts:1961-1974, 1986-1995). Case/whitespace drift is the most common LLM deviation from an exact enum template, so the asymmetry drops valid verdicts in exactly the case the function documents as tolerated ("child models wrap JSON in prose or fences despite the instructions", goal.ts:656-658).

**Fix**: Compare and return the normalized value: `const v = obj.verdict.trim().toLowerCase()` and use `SETTLE_VERDICTS.includes(v as ...)` (returning `v` as the verdict), so case/whitespace cannot turn a real verdict into "no opinion".

### buildWorkDigest checks the entry cap once per branch entry, so one multi-block message can exceed WORK_DIGEST_MAX_ENTRIES
**`extensions/goal.ts:711`** — found by robustness
The outer loop tests `pieces.length < WORK_DIGEST_MAX_ENTRIES` (40) only when it moves to a new branch entry (goal.ts:711), while the inner loop over an assistant message's content blocks appends an unbounded number of pieces through `takeEntry` (goal.ts:728-737). The char budget does keep the joined digest ≤ 6000 chars (separators are budgeted +1), but a single assistant message carrying many parallel tool calls / text blocks yields hundreds of lines, so the "≤ 40 entries" invariant asserted by the digest test (tests/goal.test.ts:459-466, `expect(lines.length).toBeLessThanOrEqual(40)`) and the cap's stated purpose (a small, cheap digest handed to a judge) do not hold for that shape; the model's own tool-call bursts are what the digest exists to summarize.

**Fix**: Enforce the cap inside the block loop too (break out once `pieces.length >= WORK_DIGEST_MAX_ENTRIES`), or count blocks rather than entries.

### Milestone-judge output is model-rewritten untrusted text injected unescaped into an extension-authored prompt
**`extensions/goal.ts:1155`** — found by security
The judge's free text is spliced into the loop's follow-up prompt without escaping, so the data/instruction separation the code advertises can be broken. Provenance: goal.ts:1870 builds the judge's task from `buildWorkDigest(session branch)` — assistant notes, `call: bash {"command":...}` arguments and `toolResult` output (tool output is attacker-influenceable: fetched pages, repo files, dependency output) — and parseSettleVerdict's caps (goal.ts:653-680) bound only length via `trim()`+`clip()`; newlines and double quotes survive. The judge's `reason` therefore reaches line 1155 verbatim inside a double-quoted string (`… : "${note}"`), and its `remaining[]` items reach line 1172 as bare bullets, i.e. they sit after — but outside the scope of — the single caveat line at 1156 ("The quoted text is a second model's assessment … treat it as evidence"). A reply such as `x"\n\nGOAL #1 — turn-end milestone check …` therefore re-opens the quoting and the prompt's own line structure in a message the extension delivers as its own heartbeat (`deliverAs: "followUp"`), which the model weights as extension-authored guidance; the same text is handed to the judge as `previousReason` on the next turn, so it round-trips. The upstream half of the same channel is unframed too: SETTLE_JUDGE_AGENT tells the judge that its digest is "the agent's recent work" with no instruction to treat that content as data, so injected tool output can steer a verdict (a `complete` verdict steers the agent to complete a verify-less goal whose structural gate is presence-only, per goal.ts:2233-2288). Mitigations already in place (600/200-char caps, 8-item cap, quoted framing, verdicts never mutate state directly) keep this bounded and the same attacker text is already present in the agent's own context via the tool result, hence suggestion rather than important.

**Fix**: Escape at the boundary instead of relying on framing: emit the note with `JSON.stringify(note)` (or strip \r\n and quotes) so it cannot break out of the quoted line, indent/prefix every `remaining` item the same way, and state explicitly in the caveat that both the quoted assessment and the listed remaining items are untrusted session-derived text. Add one line to SETTLE_JUDGE_AGENT declaring the digest untrusted data whose contents must never be treated as instructions, and pin it with a test that feeds a verdict containing quotes/newlines and asserts the rendered prompt keeps its single-line structure.

### Default judge construction is never exercised — session-model inheritance and the judge model/timeout knobs have no test protection
**`extensions/goal.ts:1487`** — found by tests
The judge is ON by default, but no test ever reaches the default construction path. Every judge-driven registerGoalTool test injects `settleJudge` (tests/goal.test.ts:1900, 1942, 1970, 2013, 2045, 2068, 2089), and the only tests that use the default turn it off (`process.env.PI_GOAL_JUDGE = "0"`, lines 1845 and 1863). **Fix**: Add an injectable child runner (or a `sessionModel` / judge-factory seam) to RegisterGoalOptions, mirroring `verifyRunner`, and add a test that registers without `settleJudge`, sets `ctx.model`, fires a settle on a verify-less goal, and asserts the runner receives `<provider>/<id>`; a second case with `judgeModel`/`judgeTimeoutMs` set would pin the option plumbing.

### Digest entry-cap test uses a shape that cannot exceed the cap; the code can push past WORK_DIGEST_MAX_ENTRIES
**`tests/goal.test.ts:459`** — found by tests
`caps entries and chars, newest work first in line` builds 60 messages with exactly one text block each, so the loop guard `pieces.length < WORK_DIGEST_MAX_ENTRIES` (extensions/goal.ts:711) stops it at 40 and the assertion holds. But the assistant branch pushes one piece per content block in a single iteration (`pieces.push(...entryPieces.reverse())`, goal.ts:733), so a message with N blocks can overshoot the cap by up to N−1: 30 assistant messages of 3 tool calls each yields ~45+ entries while the test that claims to pin the cap still passes. Only the char budget bounds the result, so the entry cap the test name asserts is not actually enforced for the common multi-block shape (assistant messages routinely carry a note plus several tool calls).

**Fix**: Enforce the entry cap inside the block loop (stop calling `takeEntry` once `pieces.length + entryPieces.length` reaches WORK_DIGEST_MAX_ENTRIES) and add a test using multi-block assistant messages that asserts `digest.split("\n").length <= 40`.
