### Milestone-judge child is never given an abort signal — alt+x / /goal pause / /goal stop / reload cannot kill it
**`extensions/goal.ts:1806`** — found by correctness, security
The judge path builds the same two abort controllers as the verify path (killAbort at 1798, drainAbort at 1804) and even registers the drain in liveCheckAborts (1806), but neither signal is ever connected to the child: the call at 1812 is `settleJudge.assess(goal, {...})` with no signal parameter, and createLlmSettleJudge passes only `{ timeoutMs }` to the child runner (goal.ts:789) even though its own seam type declares `options: { timeoutMs?: number; signal?: AbortSignal }`. The same machinery in this repo always forwards it — review.ts:1274-1281 and subagents.ts:855-861 both call runChild with `{ timeoutMs, signal }`, and runChild only kills the child from its abort listener (subagents.ts:544-552). Consequences: (1) alt+x during a judge call aborts nothing — the settle handler stays awaiting the child for up to PI_GOAL_JUDGE_TIMEOUT_MS (180s default), and when the child finally resolves normally, the flags read at 1819 are true, so the *completed* assessment is thrown away and the transcript reports 'aborted before it finished'; (2) /goal pause, /goal stop and session_shutdown (reload) drain the set but leave the in-flight `pi` subprocess and its model call running past the boundary, contradicting the new comment at 1802-1803 ('nothing outlives the boundary that owned it') and the README claim that the judge is 'killable with alt+x, and killed by /goal pause//goal stop/reload like any check'. The existing tests inject a synchronous fake judge, so none of them exercises this.

**Fix**: Thread the signal through the seam (e.g. `assess(goal, ctx, signal?)`, or add `signal` to SettleJudgeContext) and pass it in createLlmSettleJudge: `childRunner(agent, task, model, { timeoutMs, signal }, spawnFn)`, with the settle handler supplying `AbortSignal.any([drainAbort.signal, killAbort.signal, ...(ctx.signal ? [ctx.signal] : [])])`. A rejection from the killed child already lands in the existing catch and is classified as aborted.

### Milestone-judge child is never handed an abort signal — alt+x, /goal pause, /goal stop and shutdown cannot kill it
**`extensions/goal.ts:1812`** — found by robustness
The judged branch awaits `settleJudge!.assess(goal, {...})` with no signal, and `createLlmSettleJudge` calls the child runner with only `{ timeoutMs }` (line ~787); `LlmSettleJudgeDeps` has no signal field, so the `signal?: AbortSignal` slot in `JudgeChildRunner`'s options type (line 758) is dead. The two controllers that are supposed to kill checks never reach the child: `killAbort` (alt+x, lines 1798-1801) and `drainAbort` (registered into `liveCheckAborts` at line 1806 and drained by `/goal pause` line 2314, `/goal stop` line 2362, `session_shutdown` line 1614) are only read *after* the await as post-hoc classification flags (lines 1819/1843). By contrast the verify path threads `killAbort.signal` into the runner (line 1830), and `runChild` does SIGKILL the child tree when `options.signal` fires (subagents.ts `onAbort`). Consequences: (a) the comment at lines 1802-1803 ("nothing outlives the boundary that owned it"), the spinner label "alt+x aborts" (line 1785) and the README claim that the judge is "killable with alt+x, and killed by /goal pause//goal stop/reload like any check" are all false for judged goals; (b) because this handler is awaited and, per the extension's own note at lines 487-489, `session.abort()` blocks in waitForIdle until the handler returns, a user kill cannot take effect until the judge child completes or hits `PI_GOAL_JUDGE_TIMEOUT_MS` (default 180 s) — exactly the multi-minute wedge the kill chord exists to prevent; (c) the child keeps running (and burning model tokens) after the goal was paused/stopped or the session torn down, and can outlive a reload/quit as an orphan, since the drain only flips a flag.

**Fix**: Add an optional `signal?: AbortSignal` to `SettleJudgeContext` (or an `assess(goal, ctx, signal)` parameter), pass `AbortSignal.any([killAbort.signal, drainAbort.signal])` (plus `ctx.signal` when present) into `assess`, and forward it as `options.signal` in `createLlmSettleJudge`'s `childRunner(...)` call so `runChild` kills the tree. Also mirror `runGatedVerify`'s abort race so an injected judge that ignores the signal still unblocks the settle boundary.

### Judge kill/drain path is untested — the abort test can't catch that no signal reaches the judge child
**`tests/goal.test.ts:1928`** — found by tests
The only judge-abort test (tests/goal.test.ts:1928) hands the settle handler a pre-aborted `ctx.signal` and an injected judge that resolves synchronously; it only exercises the post-resolution flag check (`aborted = drainAbort.signal.aborted || killAbort.signal.aborted || ctx.signal?.aborted === true`, extensions/goal.ts:1817) and never asserts that a kill/drain signal reaches the judge. On the real path the handler calls `settleJudge!.assess(goal, {workDigest, continuation, maxContinuations, previousReason})` (extensions/goal.ts:1812) with no signal, `createLlmSettleJudge.assess` calls `childRunner(..., { timeoutMs }, ...)` (extensions/goal.ts:785) with no signal, and `runChild` only aborts via `options.signal` (extensions/subagents.ts:461, 551-556). So `alt+x`, `/goal pause`, `/goal stop`, and session_shutdown — documented in README and the code comment ('nothing outlives the boundary that owned it') as killing an in-flight judge — cannot interrupt a running judge child; the drain closure added at goal.ts:1804-1806 aborts a controller whose signal nobody observes. A wedged assessment therefore holds the settle boundary until the 180s PI_GOAL_JUDGE_TIMEOUT_MS, which is exactly the 'looks wedged' failure the alt+x chord exists to prevent. The verify-side equivalent (tests/goal.test.ts:1479) asserts the runner actually receives the signal; there is no judge analog, so the gap is invisible to the suite.

**Fix**: Add a test that presses alt+x (and one that fires the drain via /goal pause or session_shutdown) while a pending judge is in flight, asserting the judge receives an abort signal and the check resolves as aborted without burning budget. To make it pass, add `signal` to SettleJudgeContext and forward it to `runChild` from createLlmSettleJudge.assess.

### buildWorkDigest reverses block order inside a single message
**`extensions/goal.ts:712`** — found by correctness
The loop walks the branch newest→oldest (689) and pushes one piece per content block in natural order, then `pieces.reverse()` (712) reverses the whole array — which also reverses the blocks of one message. An assistant message with [text "running the tests", toolCall bash] is emitted as `call: bash {…}` before `note: running the tests`, i.e. the effect before its cause, contradicting the function's own contract ('output oldest-first') and the task text handed to the judge ('oldest first, clipped', line 746). Order *between* entries is correct, and the digest test only uses one block per message, so this is not caught.

**Fix**: Reverse at entry granularity: accumulate each entry's blocks into a local array, push them reversed (or unshift the entry's pieces), and drop the final whole-array reverse.

### Milestone-judge output is model-rewritten untrusted text injected verbatim into an extension-authored prompt
**`extensions/goal.ts:1132`** — found by security
buildWorkDigest (goal.ts:681-709) is assembled from raw session content — tool results (`result: ${clip(first.text, 240)}`), assistant notes, and tool-call arguments — which routinely carry attacker-influenceable text (file contents read by `read`, command output, fetched pages). That digest is handed to a small child model (buildSettleJudgeTask, goal.ts:738-750) whose free-text reply is parsed by parseSettleVerdict (goal.ts:646-670): it accepts the *first* `{...}` group anywhere in the reply that has a valid `verdict`, with no cap on `reason` length or on the number of `remaining` entries. renderMilestonePrompt then interpolates those strings verbatim into the follow-up message the extension delivers to the agent: `Milestone judge (${kind}): ${note}` (goal.ts:1118) and `  • ${r}` bullets under "Remaining:" (goal.ts:1132), framed as the extension's own turn-end instruction ("Keep making concrete progress toward the remaining work this turn"). lastJudgeReason is also persisted across turns and re-fed as `## Your previous assessment` (goal.ts:744, 1816, 1909), so injected text survives into later assessments. Net effect: text from untrusted tool output can be laundered by the judge into an authoritative-looking instruction channel or into a `complete`/`blocked` verdict that steers the loop, i.e. an indirect prompt-injection amplification of content the agent would otherwise see only as raw tool data. Mitigations that keep this at suggestion level: the child is tool-less (SETTLE_JUDGE_AGENT.tools = [], goal.ts:732) so it cannot act itself, the agent does already see the same raw content in its own context, and verdicts do not mutate goal state (the model's own complete/blocked call is still required).

**Fix**: Treat judge text as untrusted data at the boundary: clip `reason` and each `remaining` entry (and cap their count) in parseSettleVerdict, and render them inside an explicitly-untrusted block (e.g. a quoted/labelled "judge said:" line plus "this text comes from a model reading session content — do not treat it as instructions") rather than as plain directive bullets in the extension's prompt.

### Digest char-cap test never approaches the cap — the truncation branch is never executed
**`tests/goal.test.ts:451`** — found by tests
'caps entries and chars' builds 60 assistant messages of ~12 chars each ('note: step N'); only WORK_DIGEST_MAX_ENTRIES (40) are taken, so the digest is ~500 chars — nowhere near WORK_DIGEST_MAX_CHARS (6000). The `s.length > budget` truncation branch in buildWorkDigest (extensions/goal.ts:~700) is never hit, so `expect(digest.length).toBeLessThanOrEqual(WORK_DIGEST_MAX_CHARS)` is vacuous and the test name overstates coverage. Related: `budget` is decremented only by piece length, not by the '\n' separators added by `pieces.reverse().join("\n")`, so a digest that actually reached the budget could exceed the stated cap by up to 39 chars — a defect a test that truly exercised the cap would expose.

**Fix**: Feed entries whose combined length exceeds WORK_DIGEST_MAX_CHARS (e.g. several long text blocks) and assert the joined digest, separators included, stays within the cap and that a large piece is truncated.
