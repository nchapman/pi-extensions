## 🟠 Important

### The deferral's premise (a completion wake re-engages the agent) fails for never-ending or killed tasks, parking the goal loop
**`extensions/goal.ts:1277`** — found by correctness, security, tests
Still valid in this revision: the deferral (`const running = runningTasks(); if (running.length > 0) { setStatus/notify; return undefined; }`, goal.ts:1277-1298) returns before the continuation-cap/judge block (goal.ts:1300) and never increments `continuations`, so the park has no bound at all — no deferral counter, no wall-clock deadline. `TaskRegistry.running()` counts only `state === "running"` (lib/superbash.ts:345-349); `killTask` flips the state to "killed" with no wake (lib/superbash.ts:304-306) and `complete()` is a no-op for any non-running task ("fire-once; killed tasks never wake", lib/superbash.ts:335-337). So a task killed while the loop is parked, or a task that never exits (the tool's own docs advertise dev servers/watchers for background bash and `task_remind`), produces no wake, and the goal loop stops driving the goal for the task's whole lifetime, with only the footer `goal · holding check — N background tasks running` as a signal. The extension's own notice concedes the recovery requires a user prompt (goal.ts:1291-1294: "kill it (/tasks or task_kill): the check then runs on your next prompt"), i.e. the automatic work/check loop promised by the README is suspended indefinitely. The added tests cover only defer→calm (tests/goal.test.ts:1123-1200); the never-finishing/killed shapes are unguarded.

**Fix**: Bound the park instead of making it unconditional: record the first deferral (counter or timestamp) and after N deferrals or a grace deadline run the check anyway with a notice naming the still-running tasks, or scope the guard to tasks that can actually conflict with the verify.

### The exit→close gap is a wall-clock proxy, so an event-loop stall between the two callbacks fails a passing verify
**`extensions/goal.ts:398`** — found by correctness, security, tests
Unchanged by this diff and still valid: `runVerify` decides a verify backgrounded its work partly by comparing wall-clock timestamps stamped in two different libuv callbacks — `exitedAt` in `child.on("exit")` (goal.ts:396-398) and `const heldByDescendant = exitedAt !== undefined && Date.now() - exitedAt > EXIT_TO_CLOSE_GRACE_MS` (goal.ts:399, grace 250 ms at goal.ts:283) in `child.on("close")`. Any synchronous parent work between the two callbacks (another extension's CPU-bound handler, a large parse, a GC pause) longer than the grace makes `heldByDescendant` true for a foreground verify that exited 0, and the check is then graded as `spawnError: "verify left background processes running..."` (goal.ts:401-414): a green check is reported as a failure at the settle boundary, the loop re-engages on that false failure, and `action: "complete"` refuses a goal that is in fact met. The companion probe `groupAlive(child.pid)` on the same line is sound; only the clock comparison is a proxy. No test exercises this: the diff's new tests inject fake runners, and the real-process tests do not synthesize a stall between `exit` and `close`.

**Fix**: Keep `groupAlive(child.pid)` as the verdict and turn the timestamp gap into a bounded re-probe: after `close` with code 0, re-check `groupAlive` once after the grace window and fail only if a group member is still alive.

### setGoal's parkedForTasks reset — the fix for the silent later park — is not covered by any test
**`extensions/goal.ts:1176`** — found by tests
This diff adds `parkedForTasks = false` in `setGoal` (goal.ts:1176) specifically so that a model `set` while the loop is parked re-announces the park (the previous review's leak: the flag was cleared only in `resetContinuationBudget` and `adoptBranchState`, so a new goal inheriting a parked loop produced no notice). No test exercises that path: the deferral tests call `set` exactly once before the first park and never re-`set` while `running` is non-empty, so removing goal.ts:1176 would not fail any test and the silent-park bug would return undetected. The general 'notify once per park, re-announce after a check' mechanism is covered (tests/goal.test.ts:1140-1170), but not this trigger.

**Fix**: Extend the deferral test: park, then `execute` `{ action: "set" }` with `running` still non-empty and assert the notify fires again for the new goal (and that a subsequent settle still defers).

### The goal row still advertises the turn-end check as "Esc-abortable" — the opposite of what this change implements
**`README.md:23`** — found by correctness
The table row added by this diff says the goal's "turn-end check defers while background tasks run and is Esc-abortable" (README.md:23). The same diff's detail bullet two paragraphs down says the opposite — a bare Esc at that boundary is pi's own interrupt and popup-dismiss noise, and the check is killed with the dedicated chord `alt+x` (README.md:34) — and the code agrees: the kill listener matches `GOAL_KILL_KEY = "alt+x"` (goal.ts:224, 1366-1368), the spinner advertises "alt+x aborts" (goal.ts:1356), the settle comments state a bare Esc is pi's own interrupt at this boundary (goal.ts:1358-1364), and the `/goal pause`/`stop` handlers still note "pi exposes no abort signal at the settle boundary, so an in-flight turn-end check cannot see Esc" (goal.ts:1782-1784, 1821-1823). The doc comment for the new field repeats the stale gesture too ("True when the check was cut short (Esc / run abort)", goal.ts:128). A user who follows the table presses Esc to kill a wedged check: the run aborts pi-side (`_abortDuringBeforeSettle`), the goal's continuation is dropped, and the verify keeps running to its timeout — exactly the failure the alt+x chord exists to remove. (This clause was accurate in the prior Esc-with-confirm revision and was not updated with the switch to alt+x.)

**Fix**: Reword the row to name the real gesture, e.g. "the turn-end check defers while background tasks run and is killable with alt+x", and fix the GoalCheckDetails.aborted comment at goal.ts:128.

### The listenForTerminalInput tests discard the handler's return value, so the observe-only contract pi-tui depends on is unasserted
**`tests/goal.test.ts:660`** — found by tests
`listenForTerminalInput`'s documented contract is observe-only: it must return `undefined` so pi's own key handling still runs (goal.ts:466-489, "Observe-only — the handler returns undefined, so pi's key handling (including run abort) still sees the key"). That return value is load-bearing: pi-tui's `handleTerminalInput` stops dispatching and rewrites the key when a listener returns `{consume}` / `{data}` (node_modules/@earendil-works/pi-tui/dist/tui.js:685-699), and pi binds that listener straight into that loop (pi-coding-agent/dist/modes/interactive/interactive-mode.js:1942-1945 -> ui.addInputListener(handler)). Both new tests use a `rawInputUi` helper whose `press` does `for (const h of [...handlers]) h(data);` (line 660) and throws the result away, and the kill-key integration test does the same — so a regression where the wrapper returns the callback's value (or an intentional `{ consume: true }` to stop the key reaching the editor) would silently swallow pi's own Esc/interrupt handling and no test would fail.

**Fix**: Have `press` return the handler result and assert it is `undefined`; add a case passing a callback that returns `{ consume: true }` and assert the wrapper still yields `undefined`.
