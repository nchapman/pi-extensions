## 🟠 Important

### Legacy goal/todo state is silently abandoned: pre-upgrade sessions lose their goal and plan on reload/resume
**`extensions/goal.ts:1037`** — found by robustness
Before this change the durable state was reconstructed from tool-result `details`: the removed `scanGoalBranch` matched `type === "message"` + `message.role === "toolResult"` + `message.toolName === "goal"` + `details.goal`, and the removed `scanTodoSnapshots` read `details.todos` from todo tool results. Sessions written by those versions therefore contain no `goal.state` / `todo.state` custom entries, and the new scans read *only* custom entries — `scanCustomState` requires `entry.type === "custom"` with an exact `customType` (lib/branchstate.ts:36-42), called from extensions/goal.ts:1037 and extensions/todo.ts:360/387 — and nothing migrates the old snapshots into the new shape. On the first `/reload`, resume, or rewind of any session created before this change (pi runs these files in place and `/reload` makes edits live, so live sessions are exactly the ones that hit this): `scanGoalState` returns `goal = null`, so `adoptBranchState` clears the footer, `stopped` falls back to `false`, the settle loop's `if (!goal || goal.status !== "active" || stopped) return` (goal.ts:1333) leaves the auto-check permanently disarmed, and a model `complete` answers "Error: no goal to complete"; for todo, `reconstructFromSession` returns `[]`, so the staleness/compaction reminder never fires, recall's `planSection` yields "" (the post-compaction plan carrier silently disappears) and `/todos` shows nothing. The data is still on the branch — only adoption stops working — so the loss is silent and unreported to the user.

**Fix**: Keep a read-only fallback to the legacy details snapshots when the branch has no `goal.state` / `todo.state` entry (newest valid `details.goal` / `details.todos`), or lazily append a migrated state entry on the first adoption so old sessions keep reconstructing correctly.

### A latch derived from a terminal goal is persisted onto a brand-new active goal, silently killing the auto-check loop for it
**`extensions/goal.ts:1661`** — found by correctness
`stoppedFromState` (goal.ts:1022-1025) treats "no explicit flag" as `goal.status !== "active"`, so a branch whose newest entry is `{goal: {status: "blocked"}}` (the model's `blocked` action, goal.ts:1806, writes no latch) reconstructs `stopped = true` at adoption (goal.ts:1206) — indistinguishable from a real `/goal stop` or cap latch. The set path then bakes that derived value into the durable state of an *unrelated* goal: `persistGoalState(stopped ? true : undefined)` (goal.ts:1661) writes `{goal: active #2, stopped: true}` — exactly the "warp3090 trap shape" the docstring at goal.ts:1004-1009 defines. Trigger: model blocks goal #1 → session reload/resume (`/reload`, restart) → model `set` of goal #2 (allowed: only `paused` is guarded, goal.ts:1640; the tool is re-activated because blocked ≠ complete). Consequences: (a) the loop stays down for a fresh goal across every subsequent reload, while the *identical* sequence without the intervening reload persists `{goal: active #2}` with no latch and runs the loop — the persisted latch depends on whether a reload happened, not on what the user did; (b) the new diagnostics are false: the tool result says "the auto-check loop is STOPPED for this session (a /goal stop or the continuation cap)" and the user is told `Goal #2 set, but the auto-check loop is stopped for this session` — neither a stop nor a cap occurred; (c) the goal loses auto-continuation until the user notices the `goal · halted — /goal resume re-arms` footer and runs `/goal resume`. The `complete` variant is unreachable only because `adoptBranchState` skips `activateTool()` for completed goals (goal.ts:1207).

**Fix**: Keep the derived "loop down" out of the persisted flag: have `stoppedFromState` return the explicit flag when present and otherwise only `data.goal?.status === "paused"` (blocked/complete goals already keep the loop down via the `goal.status !== "active"` guards in agent_before_settle/turn_end), or track a separate `userStopped` flag set only by `/goal stop`, `/goal pause` and the continuation cap, and pass that to `persistGoalState`. Then a model set after a reloaded terminal goal behaves like the no-reload case and the note text is true.

### `/goal <objective>` kickoff resurrects a completed or blocked goal as active and persists it armed before any replacement exists
**`extensions/goal.ts:1934`** — found by robustness, tests
The kickoff path rewrites whatever goal is in memory — `goal = { ...goal, status: "active" }`, `stopped = false`, `persistGoalState(false)` (goal.ts:1933-1937) — *before* the model has created the replacement via the goal tool. (a) It applies to goals that `/goal resume` deliberately refuses: `resumableGoal` accepts only `paused` or `active && stopped` (goal.ts:1883-1885), so a `complete` goal or one blocked by the model's `blocked` action / by `/goal stop` is resurrected here instead. (b) The resurrection is durable: the `goal.state` entry is appended immediately, so if the model's `set` never lands (the user presses Esc right after the kickoff, the run errors, or the `set` is rejected for an invalid verify), the branch holds `{goal: <old objective>, status: "active"}` with the latch cleared. The turn-end loop then re-runs the *old* goal's verify and re-engages the agent on an objective that was already completed or abandoned (goal.ts:1333-1400), the footer starts ticking `goal · Nh` again, and continuations are consumed — a state the docs promise can only be entered deliberately by a user.

**Fix**: Do not resurrect `complete`/`blocked` goals: re-arm memory only for an existing `paused`/`active` goal, or skip the mutation and the `persistGoalState` entirely and let the model's `set` write the new state (it persists the new goal itself).

### Malformed-entry test no longer exercises the goal.state validator
**`tests/goal.test.ts:456`** — found by tests

### Durable writes on complete/blocked are never asserted
**`extensions/goal.ts:1773`** — found by tests
Both `complete` (line 1773) and `blocked` (line 1809) now call `persistGoalState()` as their source of truth, but no test inspects the appendEntry mock after either action: the `entries` array added to `makePi` (tests/goal.test.ts:91) is read only inside the four `state persistence across reload` tests (stop/pause/active/set-while-stopped). The read side is covered by hand-built fixtures (`goalState(goal({id:3,status:"complete"}))` at tests/goal.test.ts:1023), which never exercise the write. If either call were dropped, a reload would re-adopt the preceding `active` entry and resurrect a finished goal as a live, loop-armed goal — and the suite would still pass.

**Fix**: Extend the reload describe: run `complete` (and `blocked`), fire session_start with `entries`, and assert the adopted state is terminal (tool not re-activated, `agent_before_settle` undefined, footer cleared).

### The new reload tests pass with persistence deleted — they re-assert in-memory state rather than a branch round trip
**`tests/goal.test.ts:2378`** — found by robustness
All four tests in `describe("state persistence across reload")` reload by re-firing `session_start` on the *same* registration and handing makePi's live `entries` array to `sessionCtx`, but every value they assert is already in the extension closures, so they cannot fail if `pi.appendEntry`/`adoptBranchState` is removed. Concretely, in "stop survives a reload" the `stop` command has already left `goal = blocked, stopped = true`, so `agent_before_settle → undefined` and the last `setStatus("goal", undefined)` (emitted by `clearFooter()` on stop) both hold with no adoption at all; "an active goal survives a reload" and "a model set while the loop is stopped keeps the latch" likewise re-derive nothing that memory does not already hold (and none of them asserts that `appendEntry` was called, unlike the todo test's `expect(entries).toHaveLength(1)`). The todo counterpart (tests/todo.test.ts:426-436) has the same hole for its adoption assertion: the pre-reload in-memory list is already the expected one. So the suite cannot catch a broken reload even though that is exactly what these tests are named for (the scan itself is unit-covered by the `scanGoalState`/`lastTodoSnapshot` blocks and the wiring by the older `sessionCtx([...])` tests).

**Fix**: Make the reload assertion depend on the branch: seed `sessionCtx` with a state that differs from memory (e.g. a different goal id/status, or a todo list the extension never saw) and assert the adopted value, so a memory-only implementation fails.
