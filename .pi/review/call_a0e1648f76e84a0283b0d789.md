### The judge's task — a 6 KB digest of session content, including tool output — is passed to the child as a command-line argument
**`extensions/goal.ts:992`** — found by security
Carried forward from the previous review; unchanged by this diff (goal.ts is not touched here). createLlmSettleTriage calls childRunner(SETTLE_TRIAGE_AGENT, buildTriageTask(goal, ctx), model, …) (goal.ts:990-996), and buildTriageTask interpolates ctx.workDigest at goal.ts:976, which buildWorkDigest fills with assistant text, tool-call arguments and tool-result text (goal.ts:755-800, cap 6_000 chars). buildChildArgs pushes that task after `--` (extensions/subagents.ts:323-347) and runChild spawns `pi` with argv and stdio ["ignore","pipe","pipe"] (extensions/subagents.ts:516), so the full digest — including any credential passed inline on a bash command and its output — sits in the child's process argument vector, readable by other local users via ps / /proc/<pid>/cmdline and commonly captured in process-accounting and audit logs.

### parseIdleTimeoutMs still accepts any positive value, so a sub-tick window (2.9, or 300 meant as seconds) SIGKILLs every child on the first tick
**`extensions/subagents.ts:67`** — found by correctness, robustness
The numerically-zero half of the previous `parseIdleTimeoutMs` item is fixed by this diff — "0.0", "00" and "+0" now disable the watchdog via the numeric comparison at subagents.ts:65-66 (pinned at tests/subagents.test.ts:314-320) — but the other half stands and is newly pinned: the positive branch returns the raw number with no lower bound (subagents.ts:67), the new test asserts `"1500"` -> 1500 and `"2.9"` -> 2.9 as correct (tests/subagents.test.ts:324-325), `resolveIdleTimeoutMs` passes it through unchanged (subagents.ts:73-75), and the watchdog gates only on `idleMs > 0` (subagents.ts:633) with the interval floor `Math.max(100, Math.min(5_000, Math.floor(idleMs / 4)))` (subagents.ts:640). Since `lastActivityAt` is initialized at spawn (subagents.ts:507), any window at or below the 100 ms tick — `PI_SUBAGENT_IDLE_TIMEOUT_MS=1`, or `300` typed for "5 minutes in seconds" — kills every child on the first tick before a real `pi` child can emit its first stdout line (node boot plus provider connect), and the error the caller sees is "stalled: no output for 1s (request likely dead)" with no hint that the env value caused it; the subagent tools retry nothing, so every delegated task fails. The sibling knob in the same repo clamps and its test pins that floor (`clampInt(env.PI_REVIEW_IDLE_TIMEOUT_MS, 5 * 60_000, 10_000, 6 * 60 * 60_000)`, extensions/review.ts:137; `"1000"` -> 10_000, tests/review.test.ts:248) — the subagent knob has no equivalent guard.

**Fix**: Clamp the positive branch to a sane floor before returning it, e.g. `return Number.isFinite(n) && n > 0 ? Math.max(10_000, n) : DEFAULT_IDLE_TIMEOUT_MS;` (mirroring PI_REVIEW_IDLE_TIMEOUT_MS's 10s minimum), and adjust the `"2.9"`/`"1500"` expectations to the clamped values so the tests pin the guard instead of the missing one.

### The new 'leaves the watchdog off at 0' test cannot fail: the 40 ms hard timeout always beats the idle window it is supposed to observe
**`tests/review.test.ts:1250`** — found by robustness
With `timeoutMs: 40` (line 1246) every silent finder child is reaped by the hard timeout ('timed out after 0s'), which is not `isStalledError`, so `withStallRetry` (review.ts:1140-1166) never spawns a retry. All three assertions therefore hold for any implementation: `spawn.tasks` stays at `FINDER_LENSES.length`, the errors match /timed out/, and they never contain 'stalled'. They also hold if `idleTimeoutMs: 0` were coerced to the 5-minute default, because the default's first tick is 5 s away and by then the run is already `settled` (subagents.ts:635-639 returns early on `settled && !adopted`). The test's name and comment claim to pin the 0→disabled wiring through parseReviewConfig → runReview → runChild, but nothing in it can distinguish 0 from the default, so a regression there would pass CI.

**Fix**: Pin the wiring where the idle window is observable: keep the pure assertions (`resolveIdleTimeoutMs({ idleTimeoutMs: 0 }) === 0`, subagents.test.ts:330) and add a runReview test with an injected recording child runner that asserts the forwarded options carry 0, or drive one silent child with a small idle window (e.g. 20 ms, already covered at line 1163) and assert the stall/retry path while a 0 run must not take it.

### The new stand-down tests only cover balanced tool start/end pairs; the counter's underflow floor (and the unmatched-start backstop) is untested
**`tests/subagents.test.ts:650`** — found by tests
This change adds `outstandingToolRuns` to runChild and, with it, a deliberate guard: `} else if (event.type === "tool_execution_end") { outstandingToolRuns = Math.max(0, outstandingToolRuns - 1); }` (extensions/subagents.ts:551-552), commented "A duplicate end (or a malformed stream) must not underflow the count: floor at zero so the watchdog re-arms exactly when the last tool ends." The three tests added here (623, 639, 650) only ever emit balanced pairs (start+end, start+start/end/end), so none of them can distinguish `Math.max(0, …)` from a plain decrement: delete the floor and every existing test stays green. The floor is load-bearing on a realistic path, not just a theoretical "malformed stream": a chunk larger than STDOUT_BUF_MAX (1MB) makes the stdout handler discard the buffer up to the last newline before the line loop runs (extensions/subagents.ts:568-573), so a `tool_execution_start` line that shares an oversized chunk with a huge tool result is dropped while the later `tool_execution_end` is processed. Without the floor the count goes to -1, the next real `tool_execution_start` brings it back to 0, `if (outstandingToolRuns > 0) return;` is false for the whole of that next tool run, and the idle watchdog SIGKILLs a healthy child mid-tool with the "no output for Ns (request likely dead)" message — the exact failure the counter exists to prevent, with no test to catch the regression. Symmetrically untested is the documented backstop for a tool whose end never arrives ("a tool run in progress suspends the watchdog … leaving the hard timeout as the backstop there", README.md:50 / extensions/subagents.ts:275-283): no test emits a lone `tool_execution_start` with a hard timeout shorter than the idle window and asserts the child is reaped with `/timed out/` rather than `/stalled/`.

**Fix**: Add two tests next to the existing stand-down cases: (1) emit a bare `toolEndLine("ghost")` before `toolStartLine("call_1")`, then stay silent past `idleTimeoutMs` — assert the child is NOT killed (this fails if the floor is removed, because the count reaches 0 and the watchdog re-arms during the real tool run); (2) emit only `toolStartLine("call_1")` with `timeoutMs` below `idleTimeoutMs` and assert the rejection matches `/timed out/` and is not a stall error, pinning the documented hard-timeout backstop.
