## 🟠 Important

### The deferral's premise (a completion wake re-engages the agent) fails for never-ending or killed tasks, parking the goal loop
**`extensions/goal.ts:1273`** — found by correctness, robustness, tests
Carried over from the previous review; the added one-shot notice mitigates the silence but does not bound the park. `const running = runningTasks(); if (running.length > 0) { …; return undefined; }` (goal.ts:1255-1274) suppresses the check, the continuation and the cap/progress-judge decision for as long as any superbash task is in state "running". Wakes are fire-once and only sent from `registry.complete()` (lib/superbash.ts complete: "fire-once; killed tasks never wake"), while `killTask` only flips state to "killed" — so (1) after `/tasks kill <id|all>` or `task_kill` on the last in-flight task nothing ever re-engages the agent, and (2) a task that never exits is the advertised shape of `task_remind` watchers/dev servers, so the goal's loop goes quiet for that task's whole lifetime. The code's own comment concedes both cases (goal.ts:1261-1265). What the diff adds is one `ctx.ui.notify` per park (goal.ts:1266-1272) plus a footer line; `parkedForTasks` is only reset by a calm settle (goal.ts:1275), so no consecutive-deferral or wall-clock bound exists and the loop self-corrects only on a user prompt. The footer count is also stale after a kill: the goal-status text is written only at a settle, while the registry's `kill()` refreshes only the `"bg"` key (lib/superbash.ts refreshStatus), so during the park the footer keeps advertising a task that is already dead. Deferrals burning no budget and caching nothing (goal.ts:1275, 1355-1370) is correct; the missing piece is any bound on how long the loop can be held.

**Fix**: Bound the park: track when the deferral started and force the check (with a notice naming the still-running task) after a grace period, or make the registry surface settle/kill transitions to the goal loop so a killed or timed-out task triggers a settle instead of relying on a wake.

### A bare Esc aimed at another component (dialog/autocomplete dismiss) SIGKILLs the verify's process tree and re-engages the loop, because raw terminal input is accepted as the kill command
**`extensions/goal.ts:1340`** — found by security
The new settle-boundary escape hatch takes its abort from raw terminal bytes rather than from any component that owns the key: `listenForEscape` (goal.ts:465-475) subscribes to `ui.onTerminalInput` and fires on `matchesKey(data, "escape")`, and the settle handler wires that straight into the check's kill switch (`const detachEsc = listenForEscape(uiRef, () => escAbort.abort())`, goal.ts:1340), which reaches `runVerify`'s abort path and `killGroup()` — `process.kill(-child.pid, "SIGKILL")` on the check's whole process group (goal.ts:326-337, 345-348). pi-tui delivers raw input bytes to extension input listeners *before* dispatching them to the focused component (`for (const listener of this.inputListeners) { const result = listener(current); ... }` then `data = current` — node_modules/@earendil-works/pi-tui/dist/tui.js:685-700), so an Esc that pi's editor consumes to cancel an autocomplete popup or dismiss an overlay never reaches run-abort but is still seen here; the diff's own comment concedes it ("A cancel-Esc (autocomplete, dialogs) trips it too", goal.ts:1330-1335). Concretely: while a multi-minute verify runs, the user types their next message, opens an autocomplete, and presses Esc to dismiss it — input that was never addressed to the goal check — and the extension SIGKILLs the in-flight command with the user's privileges. SIGKILL is untrappable and there is no SIGTERM/grace step, so a verify that mutates state (a migration, a build that rewrites artifacts, a gate script holding locks) is torn down mid-write with no cleanup, and the handler then queues a "cut short" follow-up and returns `{ continue: true }` (goal.ts:1356-1397), re-engaging the model even though the user's Esc was aimed elsewhere. This is the input-routing half of the previously reported cancel-Esc finding: the diff removed the visible symptom (the loop no longer parks on the aborted check) but the destructive half remains, and it is the half with a persistent side effect outside the process.

**Fix**: Do not treat an arbitrary observed Esc as the kill command. Attribute it before acting — e.g. only abort when the run's own abort machinery also saw the key (check the session/run abort state on the next tick) or when no overlay/autocomplete is focused, or require an explicit double Esc / dedicated key. Independently, make the kill stoppable: send SIGTERM to the process group and SIGKILL only after a short grace window, so a verify that owns files or locks can clean up.

### An abort from /goal stop, /goal pause, or session_shutdown now re-engages the agent instead of parking the loop
**`extensions/goal.ts:1392`** — found by correctness
The new aborted branch unconditionally queues a followUp and returns { continue: true }, with no re-check of the state that changed while the verify was awaiting. /goal stop and /goal pause deliberately kill the in-flight settle check by draining the live verify controllers (goal.ts:1750, goal.ts:1789) and then set `stopped = true` / goal.status = "paused". The settle handler already passed its `stopped`/status guard at goal.ts:1244 before the await, so it reaches goal.ts:1361 with check.aborted === true and returns { continue: true } (goal.ts:1392). Nothing else aborted the session (no session.abort(), so pi's _abortDuringBeforeSettle is false), so agent-session.js:1396 honors result.continue and agent-session.js:1334 runs `agent.continue()` with the queued follow-up — i.e. one extra autonomous model turn after the user typed /goal stop, carrying a message that misreports the cause ("cut short by an Esc") and that the loop is still alive ("the next settle re-measures automatically"). Before this diff the branch returned undefined, so the run ended and the stop/pause took effect immediately. The same path fires during the session_shutdown drain (goal.ts:1170-1172) and queues a message while the session tears down. The repo's stop/pause tests only assert a standalone runVerify aborts (tests/goal.test.ts:1432, 1445), so the settle-handler interaction is uncovered.

**Fix**: In the aborted branch, re-check the halt state before re-engaging: return undefined when `stopped` is true or goal.status is no longer "active" (and skip the sendMessage entirely on the shutdown path). Keep the cut-short notice only for the still-pursuing case, and word it as a check cancel rather than an Esc.

### The exit→close gap is a wall-clock proxy, so an event-loop stall between the two callbacks fails a passing verify
**`extensions/goal.ts:387`** — found by robustness, tests
Carried over from the previous review; this hunk is untouched by the diff, but the diff's new abort path relies on the same close handler, and the defect still stands as written. runVerify decides a verify backgrounded its work partly by comparing wall-clock timestamps across two different libuv callbacks: `exitedAt` is stamped in `child.on("exit")` (goal.ts:376) and the verdict is `exitedAt !== undefined && Date.now() - exitedAt > EXIT_TO_CLOSE_GRACE_MS` (goal.ts:387, EXIT_TO_CLOSE_GRACE_MS = 250, goal.ts:271) inside `child.on("close")`. Any synchronous parent-side work (another extension's CPU-bound handler, a large parse, a GC pause) longer than 250 ms between the two callbacks makes `heldByDescendant` true for a foreground verify that exited 0, and the check is reported as `spawnError: "verify left background processes running …"` (goal.ts:392-398). Consequences: a genuinely passing check is graded as a failure at the settle boundary (the loop keeps re-engaging on a state that was actually green) and `action: "complete"` returns `NOT completed — verify …` for a goal that is in fact met. The companion signal on the same line, `groupAlive(child.pid)` (goal.ts:256-264), probes the process group directly and is sound; only the gap comparison is a proxy.

**Fix**: Do not fail an exit-0 verify on the clock comparison alone: keep `groupAlive` as the verdict and turn the gap into a bounded re-probe (after `close` with code 0, re-check `groupAlive(child.pid)` once after the grace window and fail only if a group member is still alive), so a stalled parent event loop cannot manufacture a "background processes" verdict.

### The new `details.aborted` transcript row is never asserted, so a broken abort message renders unnoticed
**`extensions/goal.ts:847`** — found by tests
`renderCheckMessage` gained the `aborted` branch at extensions/goal.ts:846-847, and it is the only thing that renders the abort notice's row: the aborted path emits a `GOAL_CHECK_TYPE` message with `aborted: true` (goal.ts:1372-1394) and the registered renderer feeds `message.details` into `renderCheckMessage` (goal.ts:1457-1463). The only `renderCheckMessage` test (tests/goal.test.ts:1959-1981) covers failed/passed/undefined with no `aborted` case, and the abort tests (tests/goal.test.ts:1333-1343 and 1386-1393) assert only `msg.content` containing "cut short" — they never read `msg.details`. A regression that drops the branch, or that emits `aborted: true` together with `ok: true`/a wrong `exitCode`, would render every aborted check as "verify passed…" or "verify failed (exit ?) — continuing" and still pass the suite.

**Fix**: Add an `aborted` case to the `renderCheckMessage` test asserting "verify aborted — re-measuring next settle", and in the Esc test assert the sent message's `details` (`aborted === true`, `ok === false`, `exitCode === null`).
