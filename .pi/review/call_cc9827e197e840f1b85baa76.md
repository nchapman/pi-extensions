## 🟠 Important

### Attachment budget mixes char counts with byte headroom, so it can overrun TASK_MAX_BYTES and truncate the diff it promises to preserve
**`extensions/review.ts:1451`** — found by correctness, tests
The per-chunk budget is `Math.min(config.attachChars, headroom)` where `headroom = TASK_MAX_BYTES - byteLength(skeleton) - byteLength(chunkText) - 2048` (lines 1447-1451) is measured in UTF-8 bytes. That number is then spent against *character* counts that undercount bytes: `selectAttachments` sums `f.chars` (line 1186), and `chars` is `piece.content.length` (line 1458) — `sliceAttachment` likewise caps with `text.length` (line 1170). `renderAttachments` adds a section header plus `### path (label)\n` per file (lines 1205-1210) that are never counted at all. For ASCII content the 2048 margin hides the header overhead, but for non-ASCII content `content.length` < UTF-8 byte length (e.g. 2x for Latin-1, 3x for CJK), so an attachment that fits the char budget can exceed the byte headroom by many KB; the rendered task then passes TASK_MAX_BYTES and `fitTask` truncates the *diff* (lines 1222-1235) — the exact outcome the new design comment promises cannot happen ('attachments never shrink the diff'). Trigger: reviewing a large diff (so headroom is the binding cap) whose changed files contain non-ASCII text (i18n/doc/binary-ish sources); reviewers silently lose changed code.

**Fix**: Do all attachment accounting in UTF-8 bytes: use `Buffer.byteLength(piece.content, 'utf8')` for `chars`, include the rendered header/separator overhead in the budget, and re-check the final `renderAttachments` string against headroom before use.

### Attachments resolve file paths against opts.cwd, not repoRoot, silently losing every attachment when the session cwd is a subdirectory
**`extensions/review.ts:1455`** — found by correctness, security, tests
The new attachment loop reads changed files with `await deps.readFile(path.join(opts.cwd, f.path))`, but every diff path is produced by `git diff` and is relative to the git toplevel, which this function already resolves into `repoRoot` (review.ts:1349) and uses for every other read (`collectGuidelines` repoRoot:1391, `untrackedSection` repoRoot:937, state read repoRoot:1399). When pi's `ctx.cwd` is a subdirectory of the repo (the command/tool pass `cwd: ctx.cwd`, lines 1706/1760), `path.join(ctx.cwd, f.path)` points at the wrong location: the read returns undefined and every attachment silently disappears, or a coincidentally-named file is attached and misleads the finder with unrelated content. All five new integration tests hardwire `cwd: "/repo"` while the git fake returns `rev-parse --show-toplevel` = `/repo` (tests/review.test.ts:248-360), so cwd === repoRoot in every case and this misbase is completely unprotected; the provided-diff seam test even sets `cwd: "/repo"` with `repoRoot: "/tmp/empty"` (line 1537) without asserting anything about attachment paths.

**Fix**: Use `path.join(repoRoot, f.path)` (repoRoot is already in scope in runReview), matching the other file reads.

## 🟡 Suggestion

### Files whose hunk windows exceed ATTACH_SLICE_MAX_CHARS are dropped silently instead of being named for the finder
**`extensions/review.ts:1170`** — found by correctness, tests
`sliceAttachment` returns null when a file's windowed slice exceeds `ATTACH_SLICE_MAX_CHARS` (16k) — the comment promises 'a window set over this (a ~400-line change) is not attached rather than partially attached.' But the file is then excluded from `read` (review.ts:1453-1458), so it never reaches `selectAttachments`, never lands in `skipped`, and is never named in the 'Files not attached (over budget — read them if needed)' fallback that README/extensions/review.ts:16 and the test suite advertise. A single-hunk change of a few hundred lines widens to a window well over 16k chars for typical source, so the finder gets neither the content nor any hint that it was omitted. No test drives `text.length > maxChars` (the `slices hunk windows` test uses 200/400 short lines, far under 16k), so this behaviour is unverified.

**Fix**: When `sliceAttachment` returns null because the window exceeds the cap, still record the file in the `skipped` list (distinct wording from budget-skips) so the finder is told to read it.
