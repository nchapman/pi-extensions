### runVerify's documented "never throws" contract leaks the shutdown-abort registration when ops.exec throws synchronously
**`extensions/goal.ts:269`** — found by robustness
runVerify registers its teardown state before it calls the backend: `outer?.addEventListener("abort", abortNow)` and `liveVerifyAborts.add(abortNow)` (goal.ts:266-268), then returns the promise chain `ops.exec(...).then(...).finally(cleanup)` (goal.ts:269-290). The cleanup lives only in that chain's `.finally` (goal.ts:285-290). If `ops.exec` throws synchronously instead of returning a rejected promise, the function throws out synchronously — the `.finally` never runs, so `abortNow` stays in the module-level `liveVerifyAborts` set forever (a later `session_shutdown` then calls `ctrl.abort()` on a dead controller) and the listener stays attached to the caller's long-lived run signal (for the settle path, `ctx.signal`, which lives for the whole session). That contradicts the contract this diff documents at goal.ts:246-249 ("Backend errors are normalized into VerifyResult ... so callers never see a throw"), and the `ops` parameter it introduces is a public seam on the exported runVerify, so a wrapper that validates/logs before delegating (`exec: (cmd, cwd, opts) => { if (!cmd) throw new Error(...); return real.exec(...) }`) reaches it. The repo's own equivalent call site guards exactly this case: lib/superbash.ts:853-865 wraps the identical `operations.exec(command, cwd, {...})` in try/catch ("Failed to start command"). The in-repo consumers happen to survive the sync throw (the settle path has its own try/catch at goal.ts:1153-1171 and the tool path catches inside the `raced` IIFE at goal.ts:1294-1299), so the concrete impact is the leaked registration/listener rather than a broken turn.

**Fix**: Move the call inside the chain so the cleanup cannot be skipped, e.g. `return Promise.resolve().then(() => ops.exec(command, cwd, {...})).then(onOk, onErr).finally(cleanup);` (or wrap the `ops.exec(...)` call in try/catch and resolve a `spawnError` VerifyResult from the catch after removing the listener/registration), matching lib/superbash.ts's guard.

### The shell's exit code is taken as the check's verdict, so a verify that backgrounds its work reports a pass while the check is still running
**`extensions/goal.ts:278`** — found by correctness
runVerify now hands the whole bound to pi's local bash backend (goal.ts:275 converts the ms bound to backend seconds) and maps a resolved `{exitCode}` straight to a verdict — `({ exitCode }) => ({ ok: exitCode === 0, ... })` (goal.ts:278) — without asking whether the shell left live processes behind. The backend's wait is deliberately #5303-safe: `waitForChildProcess` finalizes ~100 ms after the *shell* exits (EXIT_STDIO_GRACE_MS) even when a detached descendant still holds the piped stdout/stderr (node_modules/@earendil-works/pi-coding-agent/dist/utils/child-process.js:27-46,88-96), and exec's `finally` then clears its own timeout handle and calls `untrackDetachedChildPid` (dist/core/tools/bash.js:106-118) — so at the instant exec resolves, the group is neither bounded nor tracked. Trigger: a verify that puts its real work in the background (`verify: "./gate.sh &"`, a migration or server start — the same input class the previous review used for finding #2, whose comment records that the shell exits immediately while the descendant holds the pipe). That shell exits 0 ~100 ms later, so `pre.ok`/`res.ok` are true: the set preflight warns "already passes" (goal.ts:1382-1383) and, decisively, the completion gate at goal.ts:1412-1440 never takes the `if (!res.ok)` return path, so execution falls through to `goal = { ...goal, status: "complete" }` and the goal is marked complete while the gate suite/server is still running. Before this change the identical input produced `timedOut: true` (the old hand-rolled timer at goal.ts:310-312 of the pre-change code), i.e. the fix has flipped this input from a conservative verdict (false failure) to a permissive one (false pass). The leftover descendant is also exactly what the new "Nothing outlives the session" invariant (goal.ts:1015-1020) claims to cover: the verify has already resolved and its pid is untracked, so the `session_shutdown` abort closures and pi's detached-child reaper both miss the still-running tree.

**Fix**: Before returning `ok: true`, distinguish "the check ran and exited 0" from "the shell only launched work": after the shell exits, probe the group (`process.kill(-pid, 0)`) before untracking and, when it still has live members, return an inconclusive result instead of a pass (e.g. a distinct flag/spawnError such as "verify left background processes running — completion is not gated on a check that has not finished"), and/or keep the group tracked and killed so nothing a verify started outlives the session.

### The periodic tool-row progress ticker (the change's live-progress path) has no test
**`extensions/goal.ts:1292`** — found by tests
This diff's headline behavior for tool-call checks is "the model can see the check is alive": `emit()` at goal.ts:1291 fires once synchronously, and then `const ticker = setInterval(emit, VERIFY_UPDATE_MS);` (goal.ts:1292, VERIFY_UPDATE_MS = 5_000 at goal.ts:1252) is what keeps a multi-minute verify legible instead of a frozen row (see the docstring at goal.ts:1266-1272 and the README sentence added by this diff). The only test that observes onUpdate partials, `it("streams running progress onto the tool row during the set preflight")` (tests/goal.test.ts:683-699), releases the runner in the same synchronous turn and asserts `updates.length` be >= 1 and inspects `updates[0]` — i.e. only the pre-await `emit()`. There is no fake-timer usage anywhere in tests/goal.test.ts (no `useFakeTimers`/`advanceTimers`), and the two abort tests resolve the call in ~30 ms, so the interval callback never runs: deleting `setInterval(emit, VERIFY_UPDATE_MS)`, or setting the cadence to an hour, leaves the whole suite green while regressing exactly the "reads as wedged" symptom the change was written to remove.

**Fix**: Add a test with vi.useFakeTimers() that holds the runner pending, advances VERIFY_UPDATE_MS (export it, or inject the cadence), and asserts a second onUpdate partial arrives with an updated `details.running`/elapsed and that no further partial fires after the call settles.

### The pre-aborted-signal fast path in runGatedVerify is untested, so the wedge it prevents is unprotected
**`extensions/goal.ts:1303`** — found by tests
`if (signal.aborted) return ABORTED_VERIFY;` (goal.ts:1303) is the only thing that bounds the call when `signal` is already aborted before runGatedVerify runs: the race below attaches `signal.addEventListener("abort", onAbort)` (goal.ts:1305) to a signal that is already aborted, so the listener never fires, and if the runner ignores the signal (the case the diff explicitly guards — "The abort race bounds the call even if an injected runner ignores the signal") `raced` never settles and the tool call hangs with the row streaming partials forever. No test takes this branch: `it("aborts the set preflight promptly even when the runner ignores the signal")` (tests/goal.test.ts:702-714) aborts 30 ms in, i.e. *after* the listener is attached (mid-flight path), and the only already-aborted assertion is in the runVerify unit test (tests/goal.test.ts:576-584), a different function with no tool call involved. Deleting goal.ts:1303 would not fail any test in tests/goal.test.ts.

**Fix**: Add a case that calls the captured tool's execute with a pre-aborted AbortSignal (AbortSignal.abort()) and a runner that never settles, asserting the call resolves promptly with the "aborted" text and leaves the goal active.
