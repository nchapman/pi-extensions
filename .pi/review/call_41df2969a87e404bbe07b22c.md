### The settle-path verify is never Esc-abortable: ctx.signal is undefined at agent_before_settle
**`extensions/goal.ts:1240`** — found by security, robustness
Still valid after this revision — only the comments changed, the wiring did not. The settle handler still passes `signal: ctx.signal` (goal.ts:1246) into verifyRunner, and in production that value is always `undefined` at this boundary: `ExtensionContext.signal` is bound to `getSignal: () => this.agent.signal` (node_modules/@earendil-works/pi-coding-agent/dist/core/agent-session.js:2688, exposed at dist/core/extensions/runner.js:656-658), and `Agent.signal` is `this.activeRun?.abortController.signal` (node_modules/@earendil-works/pi-agent-core/dist/agent.js:214-216) with `activeRun` cleared by `finishRun()` (agent.js:381-387) in `runWithLifecycle`'s finally. `agent_before_settle` is dispatched by `AgentSession._runBeforeSettleBoundary` (agent-session.js:1384-1390) from the post-run loop of `_runAgentPrompt` (agent-session.js:1330) — after `await this.agent.prompt(...) / agent.continue()` has already returned and cleared activeRun. That is exactly why `session.abort()` needs the separate `_abortDuringBeforeSettle` flag (agent-session.js:1848-1849) rather than a live run signal. Consequences unchanged: (a) the per-turn check — the most frequent verify call site — cannot be cut short and runs to `verifyTimeoutMs` (VERIFY_TIMEOUT_MS_DEFAULT = 900_000 ms, goal.ts:194); (b) `_isAgentRunActive` stays true while the handler is awaited (`get isIdle`, agent-session.js:1029-1031), so `session.abort()`'s `waitForIdle()` (agent-session.js:1851-1857) blocks behind the handler — Esc does nothing and the session is unpromptable for up to 15 minutes, the wedge this change exists to remove and which the README still scopes away ('a heavyweight gate suite must never look wedged'); (c) the new settle test only proves the wiring with a fabricated live signal (tests/goal.test.ts:1128-1140 constructs `{ signal: ctrl.signal }` on the ctx), so it stays green in production where no signal exists, and the new `check.aborted` early return (goal.ts:1261-1267) is only reachable via the session_s…

**Fix**: Capture a live AbortSignal for the run (e.g. store the signal from agent_start/before_agent_start in a module-scoped variable) and pass it as `signal` at the settle boundary, or add an explicit Esc-driven abort hook that calls into `liveVerifyAborts`; if pi exposes no such signal yet, at minimum route `/goal stop` and the TUI Esc handler through the same abort set so an in-flight settle verify is cancellable.

## 🟡 Suggestion

### The leftover-process guard only sees the shell's own process group, so a backgrounded check can still be reported as a pass
**`extensions/goal.ts:359`** — found by robustness
This is the surviving half of the earlier finding 'The leftover-process probe and group kill only run on the exit-0 path': that half is fixed (killGroup() now runs for any exit code, goal.ts:359-361), but the guard is still blind to the shapes the new docstring (goal.ts:257-268) claims to close. The probe can only see members of the shell's own group at the instant `close` fires, and the only test covers the redirected shape (`sleep 30 >/dev/null 2>&1 &`, tests/goal.test.ts:600-607) where the pipe closes at shell exit so the leftover is still alive. (1) `verify: "./gate.sh &"` with inherited stdio: the grandchild keeps the stdout write end open, so Node's 'close' does not fire until gate.sh itself exits (this is the documented close-based wait). By then the group is empty, `groupAlive(child.pid)` is false, and `finish({ ok: code === 0 })` (goal.ts:367) reports ok:true from the SHELL's exit code — so a check that exits non-zero passes the completion gate at goal.ts:1500+ and completes the goal. The docstring's claim ('on a clean exit 0 the result is a failure, never a pass') holds only when a member is still alive at close. (2) A check that hands its work out of the group (setsid, a double-forking daemon, systemd-run, at) also leaves the group empty and is reported as a pass while the gate suite runs on. Both are defense-in-depth gaps (the verify string is model-authored and validateVerify only blocks `true`/`:`/`exit 0`, goal.ts:582-593), but they defeat the stated purpose of running the verify outside pi's bash backend.

**Fix**: Fail closed when the shell exits before its stdio is released: record the child's 'exit' timestamp and, if 'close' arrives materially later (stdio held by a descendant), treat it like the leftover branch — killGroup() and, for exit 0, report `ok: false` with the existing 'verify left background processes running' message. At minimum correct the docstring/README to state that only group members still alive at close are detected and killed, and add a test for the inherited-stdio shape (`sh -c 'exit 1' &`-style) to pin the current behavior.
