## 🟠 Important

### A single lost `tool_execution_end` line latches the new idle watchdog off for the whole run — the dead-request detector fails open
**`extensions/subagents.ts:640`** — found by security
The diff makes runChild count tool executions from the child's own stdout (`outstandingToolRuns++` on `tool_execution_start`, `Math.max(0, …)` on `tool_execution_end`, subagents.ts:552-556) and stand the stall watchdog down whenever that count is non-zero (subagents.ts:640: `if (outstandingToolRuns > 0) return;`). Only an `end` event re-arms it — the count is never correlated with `toolCallId` (pi emits it, subagents.ts:549-551 parses `type`/`message` only), never bounded, and never reset by any other event — so one start whose end line is lost pins the count ≥1 for the remainder of the run and the stall kill can no longer fire at all; only the hard timeout ends the child (default 20 min, `PI_SUBAGENT_TIMEOUT_MS` up to 6 h) and the diff's own test comment (tests/subagents.test.ts:668-670) states dropped start/end lines are real. The dropping mechanism is in the same function: the 1 MiB cap (`STDOUT_BUF_MAX = 1024 * 1024`, subagents.ts:40) discards the whole partial line when a single event exceeds it (subagents.ts:583-586), and `tool_execution_end` carries the tool's full result payload (docs/json.md:107,114 in @earendil-works/pi-coding-agent); a child that reads an image gets `{type:"image",data:encodeBase64(bytes)}` for the whole file (node_modules/@earendil-works/pi-coding-agent/dist/bundle/chunks/chunk-GUORCHFS.js:779), i.e. a single >1 MiB JSON line whose end event is dropped. Impact: the detector this change adds silently stops working for that child, so a genuinely dead LLM request burns the full hard timeout, and /review only retries `stalled` errors (`isStalledError`, extensions/review.ts withStallRetry), so the review loses its retry and surfaces a coverage gap after ~20 minutes instead of recovering. Triggering input is ordinary child output (untrusted tool content), not a condition the parent controls.

**Fix**: Make the stand-down bounded and correlated: track open executions in a Set keyed by `toolCallId` (ignore duplicate/mismatched ids), and re-arm on any event that can only follow the tool phase — an assistant `message_end` — so a counter that can never return to zero cannot outlive one request; optionally also clear the latch when the child's stdout cap discards a chunk.

### Untrusted tool output is copied raw into the judge's prompt, and the judge's verdict then steers the agent in the harness's voice
**`extensions/goal.ts:854`** — found by correctness, security
`buildSettleJudgeTask` interpolates the work digest — assistant notes, tool calls and clipped tool results (`buildWorkDigest`, goal.ts:768-818, tool output at goal.ts:803) — verbatim into the child judge's task text (goal.ts:854, and the triage twin at goal.ts:980), including the attacker-influenceable text of command output. The only defences are the child's own instruction to treat the digest as data (goal.ts:833) and the escaping/clipping of the judge's reply before it rides the parent's prompt channel (`parseSettleVerdict` caps at goal.ts:685-687; `renderMilestonePrompt` quotes with `JSON.stringify`, goal.ts:1369, 1386, and frames it as evidence, goal.ts:1371). The verdict is not inert: `complete` instructs the parent agent to summarize and call `goal complete` (goal.ts:1373-1377) and `blocked` steers it to declare an impasse (goal.ts:1378-1382), so a successful injection into the digest can terminate a goal the user did not consider done. This diff does not change the digest or the prompt, but it does add a second prompt-building call path that carries the same untrusted input, so the item is still open.

**Fix**: Wrap the digest in an explicit, closed fence (e.g. `<work-digest>…</work-digest>`) at goal.ts:854 and :983, state in the agent instructions that everything inside that fence is data, and keep the existing clip/escape on the verdict.

### The judge's task — a 6 KB digest of session content, including tool output — is passed to the child as a command-line argument
**`extensions/goal.ts:902`** — found by correctness, security, tests
This change makes runChild's idle watchdog on-by-default (resolveIdleTimeoutMs → DEFAULT_IDLE_TIMEOUT_MS) and then relies on goal.ts passing `idleTimeoutMs: 0` for both the settle judge (goal.ts:902) and the triage (goal.ts:1000) so those tool-less, long-first-token children are not SIGKILLed and re-labelled a "stalled" dead request. That exemption is the whole fix for the tool-less-child regression, yet nothing asserts it: the goal tests that stub the runner record only timeoutMs and signal — `seen.push({ agent, task, model, timeoutMs: options.timeoutMs, signal: options.signal })` at goal.test.ts:622 (asserted at :632-633) and the same shape at :2578 / :2645 — so they never read `options.idleTimeoutMs`. A future edit that drops or forgets the `idleTimeoutMs: 0` (or switches to omitting the option) silently re-arms the 5-minute watchdog on the judge/triage and no test fails; the child is killed mid-assessment and the settle boundary fails open, exactly the important regression this diff exists to prevent.

**Fix**: Pass the digest on stdin (or a temp file read by the child prompt) instead of argv for the judge/triage children, or at minimum cap the assembled task bytes and document that this content is visible in the child's command line.

### The parent's idle window is a fixed 5m that no longer matches the child's own (configurable) HTTP idle timeout, so a healthy child on a slow local model is still SIGKILLed as a 'dead request'
**`extensions/subagents.ts:38`** — found by correctness, robustness
This diff wires `idleTimeoutMs: parseIdleTimeoutMs(process.env)` into both the `subagent` (subagents.ts:951) and `subagents` (subagents.ts:1028-1033) tools, and `resolveIdleTimeoutMs` (subagents.ts:76-77) resolves an omitted value to the constant `DEFAULT_IDLE_TIMEOUT_MS = 5 * 60 * 1000` (subagents.ts:38). The child's own HTTP idle timeout is a *user setting* whose default merely happens to be 300_000 and which can be raised or disabled (documented as settable, with 0 disabling, for local models that pause longer than five minutes). The child `pi` process reads that setting, so on exactly the configuration pi blesses for slow models a child that legitimately streams nothing for >5m while waiting on its model is killed via `stall()` as "stalled: no output for Ns (request likely dead)" — the new tool-execution exemption cannot help (no tool in flight), and the only remedy is the process-wide `PI_SUBAGENT_IDLE_TIMEOUT_MS`, which loosens detection for every other child because `taskItem` accepts no per-task/per-agent idle override (subagents.ts:868-879). A healthy child is now terminated where before this change the watchdog was opt-in and such a run merely waited out its hard timeout. (The previous-review's higher-severity form of this — tool-less goal judge/triage children — is genuinely fixed by this diff: goal.ts:902 and goal.ts:1000 now pass `idleTimeoutMs: 0`, and scripts/eval-review.ts:104 too.)

**Fix**: Stop pinning the default to a constant: derive it from the run's budget, e.g. `options.idleTimeoutMs ?? Math.min(DEFAULT_IDLE_TIMEOUT_MS, Math.max(60_000, timeoutMs / 2))`, and/or add a per-task idle override so one slow child can be exempted without loosening every child.

### parseIdleTimeoutMs still accepts any positive value, so a sub-tick window (2.9, or 300 meant as seconds) SIGKILLs every child on the first tick
**`extensions/subagents.ts:70`** — found by correctness, robustness, tests
The positive branch returns the raw number with no lower bound (subagents.ts:67), the new test asserts `"1500"` -> 1500 and `"2.9"` -> 2.9 as correct (tests/subagents.test.ts:324-325), `resolveIdleTimeoutMs` passes it through unchanged (subagents.ts:76-77), and the watchdog gates only on `idleMs > 0` (subagents.ts:634) with the interval floor `Math.max(100, Math.min(5_000, Math.floor(idleMs / 4)))` (subagents.ts:641). Since `lastActivityAt` is initialized at spawn (subagents.ts:507), any window at or below the 100 ms tick — `PI_SUBAGENT_IDLE_TIMEOUT_MS=1`, or `300` typed for "5 minutes in seconds" — kills every child on the first tick before a real `pi` child can emit its first stdout line (node boot plus provider connect), and the error the subagent tools surface is "stalled: no output for 1s (request likely dead)" with no hint that the env value caused it; the subagent tools retry nothing, so every delegated task fails. The sibling knob in the same file clamps and its test pins that floor (`clampInt(env.PI_REVIEW_IDLE_TIMEOUT_MS, 5 * 60_000, 10_000, 6 * 60 * 60_000)`, extensions/review.ts:137; `"1000"` -> 10_000, tests/review.test.ts:248) — the subagent knob has no equivalent guard.

**Fix**: Clamp the positive branch to a sane floor before returning it, e.g. `return Number.isFinite(n) && n > 0 ? Math.max(10_000, n) : DEFAULT_IDLE_TIMEOUT_MS;` (mirroring PI_REVIEW_IDLE_TIMEOUT_MS's 10s minimum), and adjust the `"2.9"`/`"1500"` expectations to the clamped values so the tests pin the guard rather than its absence.
