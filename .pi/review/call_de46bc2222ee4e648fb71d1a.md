## 🟠 Important

### The deferral's premise (a completion wake re-engages the agent) fails for never-ending or killed tasks, parking the goal loop
**`extensions/goal.ts:1267`** — found by correctness, robustness, tests
The new guard `const running = runningTasks(); if (running.length > 0) { …; return undefined; }` (extensions/goal.ts:1266-1285) suppresses the check, the continuation, and the cap/judge decision for as long as any superbash task is in state "running", and it is unbounded: no consecutive-deferral counter and no wall-clock cap, and `continuations` is never incremented. The justification ("each completion wake re-engages the agent") only holds for tasks that complete — lib/superbash.ts `complete()` is fire-once and `killTask()` only flips state to "killed", and the registry header states "a killed task never wakes" (lib/superbash.ts:304-343). So a task that never exits (the tool's own docs advertise dev servers/watchers for `task_remind`, and bash `wait: "background"` has no default timeout) leaves the goal loop parked for the task's whole lifetime: the extension's documented contract ("the extension runs it at the end of every turn … and continues the agent while it fails") is silently not honoured. The one-per-park notification also promises a recovery that the same guard prevents: "If a task is killed or never finishes, send any prompt to force the check" (extensions/goal.ts:1279-1283) — but the guard reads only `runningTasks()`, so a user prompt produces a fresh run whose settle hits the same non-empty `running()` and defers again; the check is not forced while the task runs, and the footer keeps reading `goal · holding check — N background tasks running`. The new tests only cover defer→calm (tests/goal.test.ts:1128-1185) and assert the notify text only via `stringContaining("check held")`, so the never-finishing/killed shapes are unguarded.

**Fix**: Bound the park instead of making it unconditional: track the first deferral (counter or timestamp) and after N deferrals or a grace deadline fall through and run the check anyway with a notice naming the still-running tasks; and correct the notice/header text so it does not claim that any user prompt forces the check while a task is still running.

### A bare Esc aimed at another component (dialog/autocomplete dismiss) SIGKILLs the verify's process tree and re-engages the loop, because raw terminal input is accepted as the kill command
**`extensions/goal.ts:1357`** — found by correctness, security, tests
Still-valid residual of the prior security finding: the fix added a second-Esc confirmation, but the kill command is still raw terminal bytes with no attribution to the component that owns the key. `listenForEscape` (goal.ts:475-484) subscribes to `ui.onTerminalInput` and fires on `matchesKey(data, "escape")`; pi-tui dispatches raw input to extension input listeners *before* the focused component (`for (const listener of this.inputListeners) { const result = listener(current); ... }` then `data = current` — node_modules/@earendil-works/pi-tui/dist/tui.js:685-699), so an Esc consumed elsewhere is still seen here. The settle handler now aborts only when a second Esc lands within `ESC_CONFIRM_MS = 3_000` (goal.ts:224, 1355-1362), and that abort reaches `runVerify`'s kill switch: `process.kill(-child.pid, "SIGKILL")` on the check's whole process group (goal.ts:337-345). The class of input named in the finding still participates in the confirm — a single Esc with an autocomplete popup open is routed by the editor to `cancelAutocomplete()` and returns without ever invoking onEscape (node_modules/@earendil-works/pi-tui/dist/components/editor.js:601-606), i.e. it neither arms pi's abort path nor is addressed at the check, yet it arms this listener; a second popup dismissal within the 3 s window then aborts and SIGKILLs the check. Concretely: while a multi-minute verify runs, the user types their next message, dismisses the completion popup with Esc, types again, dismisses the popup again — and the extension untrappably SIGKILLs a state-mutating verify (migration, artifact rewrite, gate script holding a lock) mid-write with the user's privileges, then queues a visible "aborted before it finished" follow-up and returns `{ continue: true }` (goal.ts:1386-1415), so an Esc aimed at a popup also buys an extra autonomous model turn. The diff's own README asserts the stronger property that this implementation does not provide ("autocomplete dismissals ... must not tear down a state…

**Fix**: Attribute the key instead of counting presses: only treat Esc as a kill when pi's own run abort is also in effect, or reset `escArmedAt` on any other input between the two Escs (making them consecutive) and/or require a check-specific key.

### An abort from /goal stop, /goal pause, or session_shutdown now re-engages the agent instead of parking the loop
**`extensions/goal.ts:1389`** — found by correctness, tests
Partly fixed, still valid for session_shutdown. The new guard `if (stopped || !goal || goal.status !== "active") { updateFooter(); return undefined; }` (goal.ts:1389-1392) does cover `/goal pause` and `/goal stop`, which set `stopped = true` plus a non-active status (goal.ts:1784-1785, 1822-1823). It does not cover the session_shutdown drain: that handler only aborts live verifies and never flips `stopped` (goal.ts:1181-1183), and the state it guards (`goal`) stays active, so after a shutdown-triggered abort the code still falls through to `pi.sendMessage({content: "The goal check was aborted before it finished…", aborted: true}, {deliverAs: "followUp"})` and `return { continue: true }` (goal.ts:1393-1417). The paths that matter do not call `session.abort()` first: `reload()` emits session_shutdown and then invalidates the runner (agent-session.js:2870-2871), and `dispose()` (quit) emits it alone (agent-session-runtime.js:297-302) — unlike `teardownCurrent`, which aborts first (agent-session-runtime.js:105-106) and thereby sets `_abortDuringBeforeSettle` so the continuation is dropped (agent-session.js:1848-1849, 1394-1395). With no abort performed, `_abortDuringBeforeSettle` stays false and the `{continue: true}` is honored: a /reload that lands while a settle check is in flight leaves a stale "verify aborted — re-measuring next settle" follow-up in the queue and starts one extra model run right after the reload; on quit the queued message/run is started against a session that is being torn down. This is exactly the behavior the diff's own header says it prevents ("the administrative drains (/goal pause, /goal stop, session_shutdown) stay silent — no extra turn after a halt", goal.ts:34-35) and the comment on the guard repeats (goal.ts:1384-1388).

**Fix**: Treat shutdown as a halt too — set a flag (e.g. `stopped = true`) in the session_shutdown handler next to the abort drain, or have that handler record an abort reason that the aborted branch checks before queueing the notice and returning `{ continue: true }`.

### The cross-extension holder assumes one module instance for lib/superbash, which pi's per-extension jiti loader does not provide — the deferral can silently no-op
**`lib/superbash.ts:408`** — found by robustness
goal's default seam reads `getSharedTaskRegistry()?.running() ?? []` (extensions/goal.ts:1087) while the subagents extension writes it at registration (extensions/subagents.ts:1093), so the deferral depends entirely on both extension files resolving `../lib/superbash` to the same module instance. In a real pi run each extension file is imported through its own jiti instance with the runtime module cache disabled: node_modules/@earendil-works/pi-coding-agent/dist/core/extensions/loader.js:444-464 creates `createJitiImpl(import.meta.url, { moduleCache: false, …resolutionOptions })` inside `loadExtensionModule`, i.e. once per extension path, and jiti's `moduleCache: false` means "no runtime module cache … importing the same module multiple times" (jiti README:139-149), with `tryNative` defaulting to false (jiti lib/types.d.ts:231-237) so TS is transformed/evaluated inside that jiti instance rather than in Node's shared ESM registry. Under that loader, goal's reader and subagents' writer hold different copies of lib/superbash and the whole deferral feature never fires — and nothing reports it, because the reader's `?? []` fail-open treats "wrong module instance" exactly like "no background work", while README.md and the file header describe the deferral as working behaviour. The added tests cannot detect this: vitest imports both extensions in one module graph (tests/goal.test.ts:5, tests/subagents.test.ts:41), so publish/get share an instance there by construction; the same is true of pi's own documented cross-extension channel, `pi.events` (docs/extensions.md:86), which is what other extensions are told to use for this.

**Fix**: Verify once in a real pi session (background `sleep 60`, end the turn, and check that the footer reads `goal · holding check — 1 background task running`); if the deferral does not fire, stop relying on module identity — pin the holder on a process-global key (`globalThis[Symbol.for("pi-extensions.superbash.registry")]`) or publish/read it through `pi.events`, and add a cheap runtime assertion (or a warning when goal reads a registry instance that nothing ever wrote) so a future loader change cannot disconnect the two silently.

### The exit→close gap is a wall-clock proxy, so an event-loop stall between the two callbacks fails a passing verify
**`extensions/goal.ts:398`** — found by correctness, robustness, tests
Unchanged by this diff and still valid: `runVerify` decides a verify backgrounded its work partly by comparing wall-clock timestamps across two different libuv callbacks — `exitedAt` is stamped in `child.on("exit")` (extensions/goal.ts:385) and the verdict `const heldByDescendant = exitedAt !== undefined && Date.now() - exitedAt > EXIT_TO_CLOSE_GRACE_MS` (extensions/goal.ts:398) is computed in `child.on("close")`. Any synchronous work in the parent between the two callbacks (another extension's CPU-bound handler, a large parse, a GC pause) longer than the 250 ms grace makes `heldByDescendant` true for a foreground verify that exited 0, and the check is then reported as `spawnError: "verify left background processes running; a verify must run its check in the foreground and exit"` (extensions/goal.ts:402-410): a green check is graded as a failure at the settle boundary and `action: "complete"` returns NOT completed for a goal that is in fact met. The companion signal on the same line, `groupAlive(child.pid)`, is sound — it probes the process group directly; only the clock comparison is a proxy.

**Fix**: Keep `groupAlive(child.pid)` as the verdict and turn the gap into a bounded re-probe: after `close` with code 0, re-check `groupAlive` once after the grace window and fail only if a group member is still alive.

### parkedForTasks is cleared only by a calm settle, so a later park can still be silent although the code promises one notice per park
**`extensions/goal.ts:1277`** — found by correctness
`parkedForTasks` is set at goal.ts:1277-1278 and cleared only at goal.ts:1286, i.e. only when a settle gets past the running-tasks guard. Nothing in the goal lifecycle resets it: `resetContinuationBudget` (goal.ts:1129-1136), `adoptBranchState` (goal.ts:1138-1155) and the model `set` path (goal.ts:1160-1176) all ignore it. Sequence that leaks: goal #1 + a long task → settle defers and the notice fires (flag true) → user pauses and resumes (`/goal resume`, goal.ts:1793-1808) or the model sets a new goal while the task still runs → the next deferral reuses the stale `true` and sends no notice, so the user only sees the footer and never learns why the check is held — which is the single signal for the never-ending-task park described above. `resetContinuationBudget` is the natural boundary: a resumed/new goal should re-announce its park.

**Fix**: Clear `parkedForTasks` wherever the loop is re-armed (`resetContinuationBudget`, `adoptBranchState`, goal set/complete/stop/pause) so each new park is announced once.
