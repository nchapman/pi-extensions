## 🟠 Important

### The deferral's premise (a completion wake re-engages the agent) fails for never-ending or killed tasks, parking the goal loop
**`extensions/goal.ts:1245`** — found by correctness, robustness
The new guard `const running = runningTasks(); if (running.length > 0) { …; return undefined; }` (lines 1244–1250) suppresses the check, the continuation and the cap/judge decision for as long as any superbash task is in state "running", and the code/README justify it with "each completion wake re-engages the agent". That premise only holds for tasks that complete: superbash delivers a wake exactly once, from `registry.complete()` (lib/superbash.ts `complete`: "fire-once; killed tasks never wake"), while `killTask` only flips state to "killed" — its header states "a killed task never wakes". So: (1) after the user runs `/tasks kill <id|all>` (or the model calls `task_kill`) on the last in-flight task, nothing ever re-engages the agent — the deferred check is not merely deferred, it is never run by the loop again until a user prompt produces a settle; (2) a task that simply never exits is the advertised shape of `task_remind` ("watchers, dev servers"), and no completion wake will ever arrive for it, so a goal whose verify loop is the only driver goes quiet for the task's whole lifetime. In both cases the footer is left at `goal · holding check — N background task(s) running` (the count can already be wrong after a kill), which reads as "a check is in flight" rather than "the loop is parked". This is a behavior regression on the doc'd contract ("the extension runs it, requires it to pass before completion, and continues the agent while it fails") that only self-corrects on the next user turn.

**Fix**: Bound the deferral instead of making it unconditional: after N consecutive deferrals (or a wall-clock cap) fall through and run the check anyway, or treat the deferral as an explicit park — notify the user (and/or re-assert the footer on task kill) so a loop that will receive no wake is visible rather than silent.

### An Esc that pi handles as "cancel autocomplete"/dialog-dismiss kills the settle check and silently drops the continuation
**`extensions/goal.ts:1337`** — found by robustness
listenForEscape (goal.ts:1316, 464-466) aborts the check on *any* raw Esc, but the early return at 1337-1342 assumes pi is aborting the run ("pi drops the continuation anyway"). That assumption holds only when the editor's onEscape runs: pi-tui delivers raw bytes to extension input listeners before dispatching to the focused component (node_modules/@earendil-works/pi-tui/dist/tui.js:685-700), while pi's run abort lives in the editor handler (pi-coding-agent/dist/modes/interactive/interactive-mode.js:2331 -> restoreQueuedMessagesToEditor({abort:true})). Esc is consumed earlier by other bindings: with an autocomplete popup open the editor matches tui.select.cancel, calls cancelAutocomplete() and returns without ever invoking onEscape (pi-tui/dist/components/editor.js:601-606); same for selectors/overlays (select-list.js:124) and for bash mode (onEscape clears the editor instead of aborting). In those cases our listener still fires, runVerify resolves aborted, and the handler returns undefined: no continuation is queued, the run is *not* aborted, so nothing re-engages the model and the goal loop stops until the next user prompt or background wake. A user dismissing a completion popup while a multi-minute verify runs silently ends the loop turn (worse: no check result was recorded, lastCheck stays unset).

**Fix**: Do not treat an observed Esc as proof the run is aborting. Either confirm the abort before skipping the continuation (e.g. check session/ctx abort state on the next tick), or keep queueing the follow-up after an aborted check ("the check was cut short, re-measure") — pi drops it anyway when it really is aborting the run, so this is safe and removes the silent stall. A double-Esc or an explicit "kill the check" key would also avoid conflating cancel-Esc with abort-Esc.

### The exit→close gap is a wall-clock proxy, so an event-loop stall between the two callbacks fails a passing verify
**`extensions/goal.ts:381`** — found by correctness, robustness, tests
`runVerify` decides a verify backgrounded its work partly by comparing wall-clock timestamps across two different libuv callbacks: `exitedAt` is stamped in `child.on("exit")` (line 370) and the verdict is `exitedAt !== undefined && Date.now() - exitedAt > EXIT_TO_CLOSE_GRACE_MS` (line 381, EXIT_TO_CLOSE_GRACE_MS = 250, line 265) inside `child.on("close")`. Those are two separate event-loop turns in the parent: any synchronous work in this process (another extension's CPU-bound handler, a large parse, a GC pause) that blocks for more than 250 ms between the child's exit and the pipe-close callback makes `heldByDescendant` true for a foreground verify that exited 0, and the check is then reported as `spawnError: "verify left background processes running; a verify must run its check in the foreground and exit"` (line 390). Consequences: a genuinely passing check is graded as a failure at the settle boundary (the loop keeps re-engaging on a state that was actually green), and `action: "complete"` returns `NOT completed — verify …` for a goal that is in fact met. The companion signal on the same line, `groupAlive(child.pid)`, is sound (it probes the process group directly); only the gap comparison is a proxy.

**Fix**: Do not fail an exit-0 verify on the clock comparison alone: keep `groupAlive` as the verdict and turn the gap into a bounded re-probe (after `close` with code 0, re-check `groupAlive(child.pid)` once after the grace window and fail only if a group member is still alive), so a stalled parent event loop cannot manufacture a "background processes" verdict.
